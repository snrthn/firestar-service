# 火星财务 · 通用开发规范

> 本文只收**跨模块通用、后面还会踩**的纪律。起因是 2026-10-24 一次集中返工：
> 立项 / 发货 / 审批中心三个模块的详情布局、操作列、数据隔离各做各的，
> 虎哥要求「把通用性的记入规范，后面模块就能不再有问题」。
>
> **用法**：新模块开写前通读一遍；改完自查清单见文末。

---

## 一、列表操作列：只留「编辑 + 详情」

**规则**：列表操作列固定两位——`编辑`（按状态显隐）+ `详情`（常显）。
提交审批 / 签约 / 撤回 / 标记发货 / 标记收货 / 查看进度等**业务动作一律收进详情弹窗**。

**为什么**：操作列按钮随状态漂移会组合出三套以上的按钮组，用户每进一次页面都要重新找按钮；
同一动作散在列表和详情两处，还会导致逻辑各写一份然后漂移。

**落地要点**：

- 操作列宽度固定 `140`（两位按钮），别按最多按钮数撑宽度。
- `详情` 常显。⚠️ **不要给表格绑 `@row-click` 开详情**（2026-10-24 虎哥明确移除）：
  行点击与单元格内文本选择、复制、后续新增行内交互天然冲突，入口只留操作列按钮。
- 详情弹窗里的业务动作，**优先 emit 给列表页执行**（列表已有弹窗/校验逻辑），
  详情弹窗不复制第二份。纯确认类动作（如撤回）才由弹窗自持。
- **同一动作不要在两个入口都放**。例：审批中心「我发起的」里的立项单也走详情弹窗，
  但传 `readonly`——单据管理动作归立项管理页，否则又变成两处入口。

## 二、详情弹窗布局：不用 Tab，纵向按标题分区

**规则**：详情弹窗**一律不用 `el-tabs`**，内容自上而下按标题分区，顺序固定：

```
基本信息（el-descriptions）→ 业务明细（表格）→ 审批进度（内联时间线）
```

分区标题统一用 `<h4 class="block-title">`，**浅色渐变底 + 左侧强调竖条**做区间分隔，
样式与 `ShipmentDetailDialog` 完全一致：

```css
.block-title {
  display: flex; align-items: baseline; justify-content: space-between; gap: 10px;
  margin: 18px 0 12px; padding: 8px 12px;
  font-size: 15px; font-weight: 600; color: #303133;
  /* 主色极浅 alpha 从左向右渐隐；圆角只给右侧，左边直角避免竖条被圆角切断 */
  border-left: 3px solid var(--el-color-primary);
  border-radius: 0 4px 4px 0;
  background: linear-gradient(90deg,
    rgba(64,158,255,.16) 0%, rgba(64,158,255,.07) 45%, rgba(64,158,255,0) 100%);
}
```

`display: flex` 是为了承载「标题左 + 汇总值右」（如货物明细的合计放标题行右对齐，
不再单独占一行）；单标题场景直接用即可，无副作用。

**为什么**：详情内容一屏能读完，Tab 逼用户点三下才看全；且立项用 Tab、发货不用，
两个模块看起来像两个产品。

**改样式必须两处同步**（`ProjectDetailDialog.vue` / `ShipmentDetailDialog.vue`）。

### 限高滚动（必做）

EP 2.14 的 dialog 是多根 Fragment，`style` attr 会被静默丢弃，全局样式注入顺序不稳。
正解 = `top` prop + 内层包裹 div：

```vue
<el-dialog v-model="visible" title="XX详情" width="1000px" top="7vh">
  <div v-loading="loading" class="detail-scroll"> ... </div>
</el-dialog>

<style scoped>
.detail-scroll { max-height: calc(100vh - 280px); overflow-y: auto; padding-right: 4px; }
</style>
```

`280` = top(7vh≈75) + header(≈54) + footer(≈64) + padding(≈40) + EP margin-bottom(50) + 富余。

### 弹窗宽度：只有三档（必做）

2026-10-24 前全站有 **14 种取值**（440/480/520/560/600/680/720/760/860/900/920/980/90%+max-width…），
视觉上像十几个产品拼起来的。现统一为：

| 档位 | 宽度 | 适用 | 例子 |
|---|---|---|---|
| **S** | `480px` | 轻量表单 / 确认 / 单一意见输入（字段 ≤ 3） | 审批意见、签约、编辑别名、新建流程、插入链接、关于 |
| **M** | `640px` | 常规多字段表单 / 富文本 / 预览 / 日志详情 | 系统管理全部表单、发布反馈、文件预览、操作日志详情 |
| **L** | `1000px` | **详情页**、**带明细表格的新建/编辑**、树形分配 | 立项/发货详情、立项/发货新建、收货标记、角色权限树 |

规则：

- **不许用百分比 + `style="max-width"`**（`ShipmentCreateDialog` 的 `90%`+`1100px` 已废）——
  超宽屏会撑成巨幕；且 EP 2.14 dialog 是多根 Fragment，`style` attr 有被丢弃的风险（见第八节）。
- **`el-drawer` 的 `size` 统一 `640px`**（与 M 档同级）。抽屉是侧向工具体，不应比居中的详情弹窗还宽。
- L 档定 1000 而非 900：发货明细/立项明细的列宽和约 900–1000，1000 保证不出现横向滚动条。
- 拿不准就归 M；**宁可稍宽不要超档**——同一屏里出现第 4 种宽度就是新债。

### 滚动条纪律

- **弹窗内区块不做内嵌滚动**（时间线、明细表等）——限高滚动只留给弹窗 body 一层，
  内嵌滚动条会出现双滚动条。`ApprovalTimeline` 已按此取消 420px 限高。
- **body 滚动条统一迷你样式**（6px、圆角、灰），写法见 `ProjectDetailDialog` /
  `ShipmentDetailDialog` 的 `.detail-scroll::-webkit-scrollbar`，两处同步维护。
- 表格数据区若长（如收货子弹窗的明细表），保留默认滚动即可，迷你样式只做弹窗 body。

## 四、行级数据隔离：三段式 + DataScopeHelper

**规则**：任何「我发起的 / 我上传的 / 我的日志」语义的列表查询，必须做到
**非 ROLE_ADMIN 只能看自己的数据**，ROLE_ADMIN 看全量。

### 三段式（缺一不可）

1. **Controller**：传 `SecurityContextUtils.currentUsername(), SecurityContextUtils.isAdmin()`。
   ⚠️ 绝不从前端接收 `userId` / `username` 当过滤条件——那是越权入口。
2. **Service 方法签名**：带 `String username, boolean viewAll` 两个形参。
3. **查询构造**：`DataScopeHelper.own(wrapper, Xxx::get归属列, 归属值)`。

```java
Long me = DataScopeHelper.currentUserId(userMapper);   // 归属列是 xxxId 时
if (DataScopeHelper.denyAll(me)) {
    return new Page<>(current, size, 0);               // 查不到归属 → 空页，绝不放行全量
}
LambdaQueryWrapper<Shipment> w = new LambdaQueryWrapper<Shipment>()
        .like(kw != null, Shipment::getBatchNo, kw)
        .orderByDesc(Shipment::getCreatedAt);
DataScopeHelper.own(w, Shipment::getApplicantId, me);
```

### 归属列对照表（新模块照此选列）

| 实体 | 归属列 | 类型 | 取值方式 |
|---|---|---|---|
| `Project` | `applicantUsername` | String | `username` 形参直接用 |
| `Shipment` | `applicantId` | Long | `DataScopeHelper.currentUserId(userMapper)` |
| `FileStorage` | `uploaderId` | Long | 同上 |
| `FileDownloadLog` | `downloaderId` | Long | 同上 |
| `LoginLog` | `username` | String | `SecurityContextUtils.currentUsername()` |
| `AuditLog` | `operatorId` | Long | `DataScopeHelper.currentUserId(userMapper)` |

### 已知边界（2026-10-24 安全债已收口，见下）

- **单条接口归属校验已补齐**（2026-10-24 虎哥收口）：
  - **详情类（读）** `ProjectServiceImpl.detail` / `ShipmentServiceImpl.detail` 采用
    「申请人本人 / ROLE_ADMIN / 审批任务处理人（候选人）三选一，其余 404」口径，
    对齐 `FeedbackServiceImpl.requireVisible`（返回 404 而非 403，避免泄露资源存在性）。
    审批人在「待我审批」里点详情能正常看到，因走 `WorkflowEngineService.isCandidate`
    命中 Flowable 任务候选（含 `taskCandidateGroup` 角色段，覆盖 `ROLE_SALES_MANAGER` 之类角色审批人）。
  - **写类（改/签/标记发货/标记收货）** `update` / `sign` / `markShipped` / `confirmReceive`
    仅放**申请人本人或 ROLE_ADMIN**，**不放开审批人**（虎哥拍板：不为单一补充字段场景开放全部写权，
    需特事特办再单独处理）。越权同样返回 404。
  - `markShipped` 已叠加 `approvalStatus == APPROVED` 闸门（2026-10-24 补洞），
    防「审批没批完就发货 / 收货」整条绕过审批链。
- 隔离只管**列表**。按 id 直取的附件下载不受影响——审批人仍能看到别人传的签收证据，
  只是不会出现在自己的文件管理列表。这是有意设计。

## 五、跨模块复用详情弹窗：用 `readonly` prop

**规则**：详情弹窗在**非本人视角**下复用时，传 `readonly`，隐藏底部全部业务动作。

`ProjectDetailDialog` 与 `ShipmentDetailDialog` 均已支持该 prop，语义一致。

**判断依据**：底部动作（提交 / 签约 / 撤回 / 标记发货 / 标记收货）都是**归属人自己的动作**。
给审批人看到，点了也是后端越权报错——不如不给入口。

## 六、改字典/种子必须同步 DatabaseCheckService

**规则**：任何 Flyway 迁移里出现 `INSERT INTO sys_dict_data` / `sys_dict_type`，
**落笔即同步** `DatabaseCheckService.readSeedData` 的期望值，并在上方 Javadoc
补一笔推导链（如 `130→131`）。

**为什么**：这个常量已因「迁移改了种子数却没同步」误报**四次**（V19/V20/V22 各一次，
V32+V34+V35 一次；2026-10-24 又因 V50/V54/V56 三笔报 `130 vs 133`）。
报错文案指向「V2 未完整执行」，排查方向被带偏过。

写完迁移后自查：`SELECT COUNT(*) FROM sys_dict_data;` 与常量对一遍。

**同节补充（2026-11-04）：迁移脚本禁止硬编码库名。**
`information_schema` 守卫一律写 `TABLE_SCHEMA = DATABASE()`，不得写 `'firestar'`。
历史 `V27` / `V28` / `V75` 因此缺陷在 `firestar_test` 空库重放时误判跳过 DDL，
V75 直接报 `Unknown column 'approval_status'`；已应用迁移不可改，测试侧用
`V26.1` / `V27.1` / `V74.1` 补偿迁移规避。写新迁移时若复制旧脚本，务必检查这一处。

**期望值只有一份**：`DatabaseCheckService` 的表数 / 种子数常量已 public，
测试必须引用常量，禁止在测试文件里再抄一份数字（历史上冻结在 V39/V75 时代，
集成测试一连上真实库就集体误报）。

**枚举 ↔ 字典双向差集门禁（2026-11-05 落地，治本）**
`@Auditable.targetType()` / `operationType()` 是自由字符串，加一个字面量零成本；
字典项却要写迁移 + 同步计数常量。同一个 `audit_target_type` 字典已 4 轮人工补漏
（V22 建 6 → V69 补 4 → V98 补 1 → V201 补 `AI_PROMPT` / `AI_MODEL_CONFIG`），
「注释里写务必同步」一次都没拦住。

**新增枚举必做三步**（缺一步就会红）：
1. 代码里写 `@Auditable(targetType="XXX")`；
2. 新建 Flyway 迁移 `INSERT INTO sys_dict_data ('audit_target_type', ..., 'XXX', ...)`
   （幂等 `ON DUPLICATE KEY UPDATE`）；
3. 同步 `DatabaseCheckService.EXPECTED_DICT_DATA_COUNT` 并补一笔计数推导链。

`AuditDictConsistencyTest`（core，纯静态扫描、不连库、不需要 Spring）做**双向差集**：
「代码有字典缺」「字典有代码无（扣减 `RESERVED_*_VALUES` 显式白名单）」都直接 fail，
并带锚点断言防「路径没找到 → 空集 → 假绿」。已加入云效 `-Dtest` 白名单。
漏第 2 步 → CI 红；漏第 3 步 → `bash bin/test.sh` 的 `DatabaseCheckServiceTest` 红。

⚠️ `sys_dict_type.remark` 不要再手写完整枚举清单（V22 / V69 各维护过一份，均已过时）：
枚举唯一事实来源是 `@Auditable` 注解，字典数据以 `sys_dict_data` 为准。

**种子基线护栏（2026-11-18 落地，治「加了字典忘了改常量」）**
`/system/db-check` 是按**行数**校验种子数据的：迁移往 `sys_dict_type` / `sys_dict_data`
加了行、`DatabaseCheckService` 的常量没跟着改 → 该接口直接返回 **503 Service Unavailable**
→ 前端工作台显示「后端连接失败」、actuator 的 `databaseTable` 指标 DOWN、
启动自检刷「端口已就绪但就绪探针未通过」。报错文案与「字典」毫无关联，
排查方向极易被带偏成「后端挂了」。这个坑历史复发过 6 次（V19/V20/V22/V32+V34+V35/V214）。

**新迁移动了种子行数，必须同时改三处**（缺一处，构建期就红）：
1. 迁移脚本里加一行标记，填改完之后的**累计总数**（不是增量）：
   `-- db-check-baseline: table=51, dictType=37, dictData=162, config=14, role=9, roleConflict=4`
2. `firestar-core/src/main/resources/db/migration/db-check-baseline.properties` 的同名键；
3. `DatabaseCheckService` 的 `EXPECTED_*` 常量（并在该类注释里补一笔计数推导链）。

`DatabaseCheckSeedBaselineGuardTest`（core，纯静态扫描、不连库、不需要 MySQL）强制三条：
基线文件 ≡ Java 常量；锚点 `baselineVersion` 之后任何动了字典/配置/角色/业务表的迁移
必须带标记；版本号最高的标记 ≡ 基线文件。已加入云效 `-Dtest` 白名单。

## 七、占用 / 退还额度范式（以 shippedQty 为例）

**规则**：`item.shippedQty` 在发货申请**创建时即占用**（防并发超发）。
任何让单据**失效或减量**的路径，必须退还：

| 路径 | 处理位置 | 状态 |
|---|---|---|
| 编辑（update） | 方法开头先 release，再按新明细 occupy（顺序不可颠倒） | ✅ |
| 撤回（withdraw） | 引擎三闸通过后 release | ✅ |
| 驳回（rejectTask） | 置 REJECTED 前 release，带状态守卫防二次退还 | ✅ 2026-10-24 补 |

⚠️ **顺序坑**：编辑必须「先退后占」。颠倒则「减量编辑」会被自己的旧占用误判超发。
⚠️ 前端可用量公式：`remaining = quantity - (shippedQty - 本单自己占用)`，
编辑态要把本单占用**加回去**，否则算少。

## 八、Vue 组件：Fragment 根会吃掉 class

**规则**：组件模板**根必须是单元素**。若根是 Fragment（如内容 div + 一个 `el-image-viewer`），
调用方传的 `class` 会被**静默丢弃**，并刷 `Extraneous non-props attributes` 警告。

多根时修复方式：`defineOptions({ inheritAttrs: false })` + `useAttrs()` + 内容元素 `v-bind="attrs"`。
参见 `RichView.vue`（2026-10-23 修过一次，六个调用方的样式曾集体失效）。

## 九、审批合一工作台（待我审批）

**规则**：审批中心的「待我审批」操作列**只留一个「审批」按钮**。点开后不是独立小窗，
而是「详情弹窗 + 底部审批表单」的合一弹窗——上半看单据内容，底部直接选通过/驳回。

**为什么**：之前审批是 480px 小窗（只有意见框），审批人看不到单据就得先去别处查；
拆成「详情 / 通过 / 驳回」三个按钮，既多入口又看不全。合一后一举两得，也消灭了第二个审批 UI。

**实现约定**（2026-10-24 落地）：
- 详情弹窗加 `approvalTask?: TaskInfoVO` prop + `approved(ok)` emit。传了就进入**审批模式**：
  底部动作区整体换成 `ApprovalActionForm`（立项 / 发货两个详情弹窗**复用同一份**，不复制）。
- 审批逻辑全在 `composables/useTaskApproval.ts`（立项 / 发货两套 API 的分发与校验口径：
  驳回必填理由、多节点必选退回目标、留言空串不落库），**页面层不再持有审批 UI**。
- `ApprovalActionForm` 的 `settled(ok)` 回调：**成功才关窗**，但无论成功失败都通知父级刷新列表
  （旧任务被「重新提交」终结后继续点审批必然 400，替用户刷新才能看到新待办）。
- 普通「详情」入口（我发起的 / 历史）**务必先清 `approvalTask`**，否则会误带上一笔失败的审批任务。
- 审批模式下标题动态化：`审批 - {业务名}`。

## 十、表单交互纪律

- **危险行操作要二次确认**：删除明细行 / 删除记录这类不可逆动作，先 `ElMessageBox.confirm`
  再执行（误删一行明细会连带让合同金额、发货超发校验全错）。
- **合同金额自动带入**：立项等「明细合计 ↔ 合同金额」场景，保存前若合同金额未填（空/0）而明细合计 > 0，
  自动取明细合计兜底，避免漏填被后端打回；用户已显式填过（>0）则尊重其输入。
  「一键带入」按钮保留，供用户主动同步。
- **提交类业务动作成功后必须关窗**：详情弹窗内的提交 / 签约 / 撤回成功后 `visible.value = false`
  （不再停留），并 `emit('updated')` 让列表刷新；列表侧入口触发时详情窗本就是关的，无副作用。

## 十一、RBAC 双线模型：接口放行 与 前端按钮显隐 是两条独立链路

**规则**：权限校验有**两条互不相干**的链路，新增任何受控能力都要**两条线同时补齐**，只做一条必出 bug。

| 链路 | 作用 | 数据路径 | 校验点 |
|---|---|---|---|
| **接口放行线** | 后端 `@RequirePerm` 是否放行 HTTP 请求 | `role → sys_role_permission → sys_permission` | `AuthServiceImpl.loadPermissions`（约 440–476 行） |
| **按钮显隐线** | 前端 `v-has-perm` 是否渲染按钮 | `role → sys_role_menu → sys_menu`（`menu_type='BUTTON'` 且带 `perm_code`） | 前端指令 |

**为什么**：两条线读的是**不同的表、不同的菜单节点类型**。接口放行看 `sys_permission`；按钮显隐看 `sys_menu` 里 `menu_type='BUTTON'` 的节点。
- 若只建了 MENU 节点（类型=MENU）配了 `sys_role_permission` → 后端放行、但前端 `v-has-perm` 找不到 `BUTTON` 节点 → **页面在、按钮没**。
- 若只建了 BUTTON 节点忘了配 `sys_role_permission` → 前端按钮在、但一点就 403。

**落地要点**：
- 一份「能力」= 一个 `sys_permission`（接口侧）+ 一个 `menu_type='BUTTON'` 的 `sys_menu` 节点（`perm_code` 与 `sys_permission` 的 code 对齐）+ 在 `sys_role_menu` 授予目标角色。
- `ROLE_ADMIN` 默认要拿到全部 BUTTON 节点的授权（参考 V102/V106/V107 的写法：插入 `sys_role_menu` 把新 BUTTON 绑到 `ROLE_ADMIN`）。

**停用语义（方案 A，2026-11-05 统一）**
`sys_user.status` / `sys_role.status` / `sys_permission.status` /
`sys_role_permission.status` / `sys_menu.status` **全部参与授权计算**。
此前只有 `sys_menu.status` 参与，导致停用角色 / 停用权限 / 停用关联完全不生效
（字段存在、写入时校验取值，读取时被忽略）。

鉴权每次请求实时查库（`JwtAuthenticationFilter` → `UserRoleService` →
`PermissionResolverImpl`）、不缓存，所以任一状态置 `DISABLED` 后**下个请求即生效**，
不需要 token version、黑名单或强制踢人（那些是引入缓存 / JWT 内嵌权限快照后的事）。

- **停用角色** = 撤回该角色带来的全部角色码 / 接口权限 / 菜单 / 按钮；多角色取并集，停用其中一个不牵连其余启用角色。
- **停用权限** = 全局撤回该权限点，影响所有引用它的角色。
- ⚠️ 停用 `ROLE_ADMIN` 角色会让超管捷径同步失效（停用即降权），生产环境操作前先确认还有别的超管账号。

回归测试：`RbacStatusDisableTest`（6 个用例：启用基线 / 三种停用 / `profile()` / 多角色并集）。

## 十二、新增后端模块（如 AI 提示词管理）必须配套 BUTTON 菜单节点

**规则**：每新增一个带写操作的后端模块页面（典型：AI 模型配置、AI 提示词管理），除了建「页面 MENU 节点」和 `sys_role_permission`，**必须再建该页面下的 BUTTON 菜单节点**（`menu_type='BUTTON'`，`perm_code` 对齐接口权限 code），并把它们授给 `ROLE_ADMIN`。

**为什么**：这是「双线模型」的具象翻车点。V106 给提示词管理建了页面 MENU + `sys_role_permission`，却漏了 BUTTON 节点 → admin 能看到页面、但新增/编辑按钮被 `v-has-perm` 全部藏掉（「页面在、按钮没」）。V102（模型配置）、V107（提示词按钮）都是同一类补丁：**补 BUTTON 节点 + 授 ROLE_ADMIN**。

**落地要点（迁移模板）**：
```sql
-- 1) 页面下的按钮节点（以 9502 提示词页为例，节点号 95021~95024）
INSERT INTO sys_menu(id, parent_id, menu_name, menu_type, perm_code, route_path, ...)
  VALUES (95021, 9502, '提示词-新增', 'BUTTON', 'ai:prompt:add',  NULL, ...),
         (95022, 9502, '提示词-编辑', 'BUTTON', 'ai:prompt:edit', NULL, ...);
-- 2) 授给 ROLE_ADMIN（否则 admin 自己都看不到按钮）
INSERT INTO sys_role_menu(role_id, menu_id)
  SELECT 'ROLE_ADMIN', id FROM sys_menu WHERE menu_type='BUTTON' AND id BETWEEN 95021 AND 95024;
```

## 十三、菜单 route_path 必须以 `/` 开头

**规则**：所有 `sys_menu.route_path` **必须以 `/` 开头**（如 `/system/prompt-config`）。

**为什么**：前端 `el-menu` 的 router 模式用 `index = route_path` 跳路由。若 `route_path` 缺前导 `/`（如 `system/prompt-config`），会被 Vue Router 当作**相对当前路由的路径**解析——从 `/system/*` 页面点进去会变成 `/system/system/prompt-config`，命中全局 catch-all → **403**。

**落地要点**：
- 新增/修正菜单迁移时，写 `'/system/xxx'` 而非 `'system/xxx'`。V108 就是修 `route_path='system/prompt-config' → '/system/prompt-config'` 这一处。
- 附带要求：种子校验（见第十节 `DatabaseCheckService`、第十三节 `SeedIntegrityValidator`）应把「`route_path NOT LIKE '/%'`」列为校验项，启动/CI 即发现漏写。

## 十四、跨项目数据范围：写操作必过闸，只读接口靠权限设计约束

**规则**：任何「按 id 直取单条」的详情/写接口，若不是纯公开资源，都必须显式归属校验；
**写操作（反核销、删除、状态变更等）无论列表是否已隔离，都要在方法内二次过闸**。
只读类汇总/分页接口若依赖「类级 `@RequirePerm`」做隔离，则**对应的权限点（如 `writeoff:*`）
在设计上只能授予财务 / 管理员角色**，并在 RBAC 配置里写死，不得下放给普通业务人员。

**为什么**：列表页的 `DataScopeHelper` 过滤只拦列表查询，**绕不过「按 id 直取」的详情/写接口**——
任何人拿到一个有对应权限点的会话，遍历 id 就能横向读取或破坏他方数据（越权）。反核销这类
破坏性写操作一旦越权，可直接篡改他方账目。

**落地要点**：
- 写操作过闸范式（参照 `ReceivableServiceImpl.detail`、`WriteOffServiceImpl.reverse`）：
  `if (!isAdmin() && !Objects.equals(归属列, currentUserId())) throw 404;`（安全失败，宁缺毋滥）。
- 只读接口若接受任意 `projectId` / 全库查询，必须在《RBAC 权限分配说明》里明确「仅财务角色可授」，
  并由 `SeedIntegrityValidator` / 人工审计兜底，防止误授业务人员导致横向越权。
- 新增「按 id 操作」接口时，先在本文第十节对照表确认归属列，详情/写接口自行比对归属。
