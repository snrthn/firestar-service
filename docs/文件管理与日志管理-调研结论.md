## 一、现状盘点（有据可查）

### 1.1 技术栈基线

| 层 | 现状 |
|---|---|
| 后端 | Spring Boot 3.3.4 / Java 17 / MyBatis-Plus 3.5.7 / Flowable 7.1.0 / Spring Security 6 + JWT / Flyway / MySQL / Hutool |
| 前端 | Vue 3.5 + Vite 5 + Element Plus 2.14 + Pinia + axios |
| 路由 | **后端菜单驱动的动态路由**（RuoYi 风格）：`/auth/menus` 授权集 → `router.addRoute`，视图按 `sys_menu.component` 字符串 glob 匹配 |
| 权限 | `@RequirePerm(perm_code)` + `PermissionInterceptor` 全局拦截；未标注 = 公开（仅要 JWT）；`ROLE_ADMIN` 直通 |
| 配置 | `application-{dev,test,pre,prod}.properties` + `.env/<profile>.env`（`set -a; source` 注入环境变量）→ `${...}` 占位符；默认 profile 是 **prod** |
| 环境 | dev / test / pre / prod 四套，AK/SK 类密钥一律走云效 Secrets，明文不入库 |

### 1.2 两个模块的落地缺口

| 维度 | 文件管理 | 日志管理 |
|---|---|---|
| 菜单（`sys_menu`） | ✅ id=18 `/system/file`，`component=system/file`，`perm=file:manage` | ❌ **无菜单、无 `log:*` 权限点** |
| 权限点（`sys_permission`） | ✅ `file:view` / `file:manage` | ❌ 无 |
| 前端页面 | ⚠️ `views/system/file.vue` 仅 4 行 `PagePlaceholder` 占位 | ❌ 无 `log.vue` |
| 数据表 | ✅ `sys_file_storage` + `sys_file_download_log` | ⚠️ 仅 `sys_audit_log`；**无登录日志表** |
| 实体 / Mapper | ✅ `FileStorage` / `FileDownloadLog` + 两个 Mapper | ✅ `AuditLog` + Mapper |
| Service / Controller | ❌ 无 | ❌ 无 |
| **写入方** | ❌ 无（Mapper 从未被调用） | ❌ **无——审计日志「表建好了但没人写」** |
| pom 依赖 | ❌ 无 OSS SDK | — |
| multipart 配置 | ❌ `application.properties` 未配 `spring.servlet.multipart.*` | — |

**关键结论 1：** 两个模块都处于「骨架已铺、血肉全无」状态。文件管理是「菜单/表/实体齐了，缺实现」；日志管理是「连菜单都没有，且审计日志零写入」。

**关键结论 2（`AuditMetaObjectHandler` 的语义陷阱）：** 它名字带 Audit，实际**只填充 `version`/`createdAt`/`updatedAt` 公共字段**，不写一行审计日志。代码注释里也明确写了 `createdBy`/`updatedBy` 暂不填。别把它当成审计日志的写入点。

**关键结论 3（应用日志的真实隐患）：** 项目**没有 `logback-spring.xml`**，应用日志全靠 `bin/start.sh` 的 shell 重定向前台 stdout 追加到 `logs/app.log`。实测该文件已 **291 MB** 且无滚动、无切割、无归档。这不是「日志管理」的功能问题，是运维地雷，建议顺手一起收。

### 1.3 需求侧硬约束（来自需求文档与纪律红线）

- **红线 4（高危）**：文件不能存数据库，存磁盘/对象存储，DB 只存路径；命名 `项目编号+类型+日期`；**销售只能下载自己项目的发票**；需归档与清理策略；上传要校验格式和大小。
- **红线 5（致命）**：所有金额/状态变更必须可追溯；**审计日志不可删除、不可篡改**；至少覆盖：立项创建、审批通过/驳回、金额改前改后、谁上传了什么、谁下载了什么+时间、谁登录了+IP。
- **需求 V1.2**：「系统应记录**登录日志和操作日志**，全程审计用户行为」。
- **业务模型**：文件下载记录保留 **90 天**后清理；清理无引用的临时文件；30 天未提交草稿清理。
- **技术栈文档**：文件存储 V1 本地磁盘、V2 才上对象存储（MinIO），并明确要求「**FileStorage 接口抽象，切换不改业务代码**」。→ 现在提前接阿里云 OSS，正好落到这个抽象上，**不违背原设计**。

### 1.4 接口文档已规划的文件管理 5 个 API

`POST /api/files/upload`（已登录）、`GET /api/files/{id}`、`GET /api/files/{id}/download`（记录下载日志）、`DELETE /api/files/{id}`（管理员）、`GET /api/files/{id}/download-logs`（管理员）。另有 `GET /api/audit-logs`（审计日志列表）。
→ 实施时**直接对齐这 5 个 API**，不要另起炉灶。

## 二、文件管理设计

### 2.1 总体架构：存储抽象 + 环境隔离

```
Controller (FileController)  ← @RequirePerm("file:manage")
        ↓
FileService（业务编排：权限校验 / DB 记录 / 下载日志）
        ↓
FileStorageService  ← 接口（技术栈文档已要求的抽象）
   ├── LocalStorageServiceImpl   （dev，@ConditionalOnProperty type=local）
   └── AliyunOssStorageServiceImpl（test/pre/prod，type=oss）
```

切换只改配置 `firestar.storage.type`，业务代码零改动——这是原技术栈文档就定好的契约，现在接 OSS 是顺势落地。

### 2.2 阿里云 OSS 接入方案

**（1）依赖**：`com.aliyun.oss:aliyun-sdk-oss`（3.x，Java 17 兼容）。可选官方 `aliyun-oss-spring-boot-starter`，但自动装配对「多环境不同 Bucket + 自定义 Key 规则」反而束手，建议**直接用 SDK + 自建配置类**，控制力更强。

**（2）环境隔离（重点要求）—— 推荐「Bucket 硬隔离 + 前缀软隔离」双保险**

| 环境 | Bucket | Key 前缀 | 说明 |
|---|---|---|---|
| dev | `firestar-dev`（或本地磁盘） | `dev/` | 本地起服用磁盘也行，不强制上云 |
| test | `firestar-test` | `test/` | 与生产**完全物理隔离** |
| pre | `firestar-pre` | `pre/` | 预发贴近生产，用独立 Bucket |
| prod | `firestar-prod` | `prod/` | 生产，生命周期规则 + 合规保留 |

- **只做前缀隔离是「软隔离」**：一次配置写错（比如 test 环境误配 prod 的 base-dir）就会把测试文件写进生产目录，且**清理任务如果按前缀删，可能误删生产数据**。分 Bucket 后，即使前缀写错，RAM 策略也会在权限层拦住——这是硬隔离的价值。
- 代价：多几个 Bucket（OSS 本身不按 Bucket 数收费，只按存储量和请求数）。**建议采纳**。

**（3）ObjectKey 规则**

```
{bizType}/{yyyy}/{MM}/{dd}/{uuid}.{ext}
实际落盘：oss://firestar-prod/invoice/2026/10/15/8f3c2a1e...pdf
```
- `uuid` 保证唯一，杜绝覆盖——**OSS 同名 PutObject 会静默覆盖，是经典事故源**。
- 红线 4 要求的「项目编号_类型_日期」规范，落在**展示名**（DB `original_name`）与归档检索上，不落进 Key（Key 里塞业务字段，重命名为乱码就难回溯）。
- 单文件建议 ≤ 20 MB（财务回单/发票 PDF 通常 < 10 MB）。

**（4）配置注入（严格对齐现有 `.env` 机制，AK/SK 绝不入库）**

```properties
# application-{profile}.properties
firestar.storage.type=${STORAGE_TYPE:oss}
firestar.storage.local.dir=${LOCAL_STORAGE_DIR:./uploads}
firestar.storage.oss.endpoint=${OSS_ENDPOINT}
firestar.storage.oss.bucket=${OSS_BUCKET}
firestar.storage.oss.access-key-id=${OSS_ACCESS_KEY_ID}
firestar.storage.oss.access-key-secret=${OSS_ACCESS_KEY_SECRET}
firestar.storage.oss.base-dir=${OSS_BASE_DIR:prod}
spring.servlet.multipart.max-file-size=20MB
spring.servlet.multipart.max-request-size=50MB
```
`.env/example.env` 同步补占位键；真实值走云效 Secrets。命名与现有 `DB_URL/DB_USERNAME` 风格保持一致。

**（5）上传链路：V1 服务端中转，V2 演进 STS 直传**

| 方案 | 适用 | 理由 |
|---|---|---|
| **服务端中转（V1 推荐）** | < 20 MB 常规文件 | 权限校验全在后端；「文件落 OSS + DB 记录」可在同一事务语义内完成，不会出现孤儿对象；实现简单 |
| STS 临时凭证前端直传（V2） | 大文件 / 高并发 | 前端拿后端签发的 STS Token（900s 有效期、限定 bucket+prefix+content-length-range）直传，减轻服务器带宽；**代价是要做回调确认，回调丢了就产生孤儿对象** |

财务系统 V1 文件小、并发低、合规要求高 → **先做中转**。等真出现大附件或带宽瓶颈再上 STS，抽象层已在，改造只动 `upload` 实现。

**（6）安全校验（对应红线 4）**
- 扩展名白名单 + **内容嗅探**（Tika 或读 magic number）双重校验，防 `.pdf.exe` 伪装；
- 大小上限（配置化）；
- 原始文件名**绝不拼进 Key**（防路径穿越 `../` 与编码坑），DB 单独存 `original_name` 供展示；
- 下载走**业务权限校验**（`PermissionResolver`）：销售只能下自己项目的发票——`bizType + bizId` 反查项目归属，越权返回 403，而不是靠「猜不到 URL」；
- Bucket 设为**私有读写**，下载统一由后端签发**带时效的签名 URL**（如 10 分钟）或后端流式代理，不暴露公网直链。

### 2.3 表结构补充（Flyway V19）

`sys_file_storage` 现有字段不足以支撑 OSS 多环境，建议补：

| 新增列 | 类型 | 用途 |
|---|---|---|
| `storage_type` | VARCHAR(16) | `local`/`oss`，迁移与排查必需 |
| `bucket_name` | VARCHAR(64) | 多环境不同 Bucket 时必须 |
| `original_name` | VARCHAR(255) | 原始文件名（展示 + 命名规范溯源） |
| `file_hash` | VARCHAR(64) | SHA-256，完整性校验 / 去重 / 秒传 |
| `status` | VARCHAR(16) | `NORMAL`/`ARCHIVED`，支撑归档策略 |
| `download_count` | INT | 冗余计数，避免列表页联表 count |

> 注意：`storage_path` 保持不动，注释已写「磁盘或 OSS Key」，语义兼容。新增列走 **V19 增量脚本 + 同步 `FileStorage.java` + 同步 `建表方案.md`**（项目既有红线：DDL / 实体 / 建表方案三处对齐）。

### 2.4 删除语义与清理

- DB **软删除**（`LogicDeleteEntity`），OSS 对象**不立即删**——财务凭证有合规保留期；
- 删除动作本身要写审计日志（红线 5）；
- 定时清理（`@Scheduled`，项目暂无调度框架，先用 Spring 原生）：
  - 下载记录：**90 天**（业务模型明确要求）；
  - 无引用临时文件：30 天；
  - 清理任务必须按 `bucket + env 前缀` 严格限定范围，**先 dry-run 打印再真删**。

## 三、日志管理设计

### 3.1 三层日志模型（成熟项目通行做法，对齐 RuoYi 的 `operlog` + `logininfor`）

| 层 | 载体 | 现状 | 说明 |
|---|---|---|---|
| ① 登录日志 | `sys_login_log`（**新增表**） | ❌ 缺失 | 谁、何时、IP、UA、结果（成功/失败/被顶下线）、失败原因。需求 V1.2 明确要求 |
| ② 操作日志 | `sys_audit_log`（已有表） | ⚠️ 零写入 | 操作人、类型、目标、改前/改后 JSON、IP。对应红线 5 |
| ③ 运行/异常日志 | logback → 文件 | ⚠️ 无配置文件 | 建议补 `logback-spring.xml` 滚动切割，ERROR 级可选异步落表 |

### 3.2 写入机制（核心设计）

**操作日志用 AOP，不要在每个 Service 里手写。**

```java
@AuditLog(operation = "UPDATE_AMOUNT", targetType = "RECEIVABLE",
          recordBefore = true, recordAfter = true)
public void updateAmount(Long id, BigDecimal amount) { ... }
```

- 自定义 `@AuditLog` 注解 + `@Around` 切面，自动抓取 before/after 快照（JSON `Map`），业务代码零侵入——这是 RuoYi `@Log` 的成熟套路；
- **必须在事务提交后写**：用 `TransactionSynchronizationManager.registerSynchronization(...).afterCommit()`。否则会出现「业务回滚了，审计日志却留下了」的不一致——审计日志本身就是取证凭证，不能比业务数据还不准；
- **异步写入**：`@Async` 或独立线程池，避免日志 IO 拖慢主流程（异步 + afterCommit 组合，顺序上要在 afterCommit 里提交异步任务）；
- 登录日志：埋在 `AuthService.login` 成功/失败分支 + `JwtAuthenticationFilter`（失败/被顶下线场景）；
- 运行日志：`GlobalExceptionHandler` 里对未捕获异常落 ERROR 级日志。

### 3.3 「不可删除、不可篡改」怎么落地（红线 5）

| 手段 | 做法 | 成本 |
|---|---|---|
| 表结构 | `sys_audit_log` 本就**无 `is_deleted`**（第五层：只增不删不改），保持 | 已满足 |
| 接口层 | **只暴露 GET 列表，不提供任何删/改接口** | 低，必做 |
| 权限层 | `@RequirePerm("log:manage")`，仅管理员 | 低，必做 |
| 应用日志 | 无 `logback` 配置时无法追溯，建议补 | 中 |
| hash 链防篡改（V2 可选） | 每条带 `prev_hash`，形成链式校验 | 高，合规加分项 |

V1 做到「无删改接口 + 仅管理员可见 + 只增表结构」即可满足红线；hash 链留到有强合规审计需求时再说。

### 3.4 菜单与权限（Flyway V19 一并种入）

```sql
-- 权限点
('log:view','日志查看','API','READ','ENABLED',0),
('log:manage','日志管理','API','WRITE','ENABLED',0),
-- 菜单：系统管理(id=12) 下新增
(19,'日志管理',12,'/system/log','system/log','log:view','MENU',7,1,'ENABLED',0);
```

前端新建 `views/system/log.vue`，建议**单页三 Tab**（登录日志 / 操作日志 / 下载日志），比拆三个独立菜单更省维护；下载日志直接复用已有的 `sys_file_download_log`。

### 3.5 前端改造点（文件管理）

`views/system/file.vue` 从 4 行占位换成真页面：上传（el-upload，带进度/类型限制）→ 列表（分页 + bizType 筛选）→ 下载（签名 URL）→ 删除（管理员）→ 下载记录抽屉。新增 `api/file.ts`，复用现有 `utils/request.ts`（已处理 JWT 注入与 401 会话守卫）。**路由/菜单不用动**——动态路由会自动把 `system/file` 解析到该文件。

### 验证方式（对齐项目既有纪律：验证通过才宣称完成）

1. 编译 + `vue-tsc` 类型检查全绿；
2. 冒烟：上传 → 列表 → 下载 → 删除 全链路；**跨环境核对 objectKey 前缀/Bucket**（test 与 prod 必须落在不同位置，这是硬验收点）；
3. 权限：无 `file:manage` 的角色调删除接口 → 返回 `code=403`；
4. 审计闭环：改一笔金额 → `sys_audit_log` 出现记录且 `before_value`/`after_value` 正确；**业务回滚时日志不得残留**（afterCommit 的验证点）；
5. 登录：成功/失败/被顶下线三种场景都有 `sys_login_log` 记录且 IP 正确。

## 五、最终锁定方案（三轮对接后定案 2026-10-16）

### 5.1 已定决策

| # | 决策项 | 最终结论 | 依据 |
|---|---|---|---|
| 1 | Bucket 划分 | test/pre 共用 **fire-star-stage**（前缀 `test/` 与 `pre/` 区分）；prod 用 **fire-star-prod**；dev 本地磁盘 | 虎哥已建好两桶。共用 stage 可接受，但清理任务必须按 bucket + 前缀双重限定范围 |
| 2 | 地域 | Bucket 华北2（北京）、ECS 张家口 → **跨地域，保持现状** | 控制台无张家口 OSS 选项 |
| 3 | 上传链路 | **服务端中转** | 上传流量一律免费（增量成本 0）；能保证「落存储 + 写 DB」一致，不产生孤儿对象 |
| 4 | 下载链路 | **后端签发时效签名 URL，浏览器直连 OSS** | 跨地域中转要付两次流出费（OSS 外网流出 + ECS 出方向），还占 ECS 出网带宽 |
| 5 | 访问域名 | 已备案自定义域名 **oss.snrthn.com** | ① 2025-03-20 起新 Bucket 不能用默认外网域名调数据类 API；② 默认域名访问会被浏览器强制下载、无法预览 |
| 6 | 日志 UI | 两个**一级目录**各挂子菜单（不是 Tab） | 文件/日志是横切能力，符合 V6「按业务场景分组」的设计意图 |
| 7 | 主页面命名 | **「文件列表」**（不是「文件预览」） | CATALOG 本身无页面，主功能页面必须落在某个子菜单上 |
| 8 | 权限粒度 | 菜单粒度 ≠ 权限粒度：CATALOG 不带权限点，子菜单共享 `file:view` / `log:view` | 保持项目「一个模块一个权限点」的约定 |
| 9 | logback 滚动 | 待办（P3） | `logs/app.log` 已 291MB 无切割 |

### 5.2 最终菜单结构

| id | 菜单 | 类型 | parent | route | component | 权限点 |
|---|---|---|---|---|---|---|

### 5.5 自定义域名实测结论（2026-10-16）

域名归属变更后做了四轮实测，结论如下：

| 验证项 | 结果 | 证据 |
|---|---|---|
| CNAME 归属 | ✅ `fire-star-prod.oss-cn-beijing.aliyuncs.com` | 本地 DNS + 公共 DNS 223.5.5.5 均一致 |
| 自定义域名绑定是否生效 | ✅ 生效，PUT/GET 均 200 | 以 `http://oss.snrthn.com` 为 endpoint（is_cname=true）读写 `fire-star-prod` 成功 |
| **HTTPS 可用性** | ⛔ **不可用** | 服务端返回区域默认证书，`CN=cn-beijing.oss.aliyuncs.com`，SAN 全是 `*.aliyuncs.com` 系列，**不含 `oss.snrthn.com`** → `CERTIFICATE_VERIFY_FAILED` |
| 图片预览（自定义域名） | ✅ 无 `Content-Disposition`，可 inline 预览 | 实测 PNG 响应头 `Content-Disposition = None` |
| 图片预览（默认域名） | ❌ 强制 `attachment` | 实测 PNG 响应头 `Content-Disposition = 'attachment'`，且签名参数 `response-content-disposition=inline` **压不过它** |
| PDF 预览（默认域名） | ✅ 不受影响 | 该限制只作用于 web 类文件（图片/HTML） |

**两条被实测推翻 / 修正的先前结论：**

1. 「2025-03-20 起新 Bucket 不能用默认外网域名调数据类 API」——**本项目两个桶均未触发**，默认域名 PUT 直接 200。故自定义域名不是上传的刚需，只是**预览**的刚需。
2. 「一个域名可借 CNAME 给多个桶复用」——**不成立**。OSS 签名把 Host 算进 `StringToSign`，用绑了 A 桶的域名签 B 桶请求必 403。所以 `oss.snrthn.com` 绑 prod 之后，**test/pre（fire-star-stage）永远用不了这个域名**。

**为什么现在不启用 `public-domain`：** 只剩 HTTP 一条路可走，而 HTTP 意味着财务文件明文传输 + 前端 HTTPS 页面按混合内容拦截，两条都不可用。因此 `application-prod.properties` 里保持 `public-domain` 为空（回退默认域名，下载功能完全正常，仅图片不能在线预览），把启用开关预置在 `.env/prod.env` 里。

**启用三步（证书托管完成后，无需改代码）：**

1. 数字证书管理服务申请「个人测试证书」（免费，90 天）或复用 `snrthn.com` 现有证书，域名填 `oss.snrthn.com`，下载 PEM/KEY 格式；
2. OSS 控制台 → `fire-star-prod` → 传输管理 → 域名管理 → **证书托管** → 上传公钥 + 私钥；
3. `.env/prod.env` 里取消 `OSS_PUBLIC_DOMAIN=https://oss.snrthn.com` 一行的注释。

> 关于协议：代码里 `public-domain` 不带协议时会**继承 `endpoint` 的协议**，不写死 https —— 避免配了域名却没配证书时抛出指向不清的 SSL 异常（且 `OSSClientBuilder.build()` 阶段不发请求，启动不会报错，只有首次上传才炸，极易误判成 AK/SK 问题）。

**待虎哥决策：** 是否需要为 `fire-star-stage` 再绑一个子域名（如 `oss-stage.snrthn.com`）。若需要，test/pre 才有图片预览；若测试环境无所谓，保持现状即可（PDF 预览与全部下载功能不受影响）。
