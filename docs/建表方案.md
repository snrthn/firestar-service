## 一、设计目标与核心原则

### 1.1 目标

| 目标 | 落地手段 |
|---|---|
| **开箱即用**（无人值守建库） | Flyway `V1__baseline.sql` 一把建全量表 + 基础字典 |
| **可扩展**（后期字段补充） | 三层预留机制，见 §4 |
| **不误删钱** | 五层删除策略 + 逻辑删除三字段 |
| **账对得上** | 金额 `DECIMAL(18,2)` 全局统一 + 核销单事务 |

### 1.2 硬约束（三份文档一致口径，不可违背）

1. 金额一律 `DECIMAL(18,2)`，Java 侧 `BigDecimal`，前端 `decimal.js`，**禁用 float/double**
2. 核销是**单事务**：改收款已核销 + 改应收已核销 + 插核销记录，三者同成同败
3. **红冲从不 UPDATE 原金额** —— 一律「新增反向记录 + 关联回原记录」，审计链完整保留
4. 权限校验**必须后端拦截器**执行，前端隐藏按钮只是体验优化
5. 禁止在代码里硬编码枚举值 → 统一走字典表
6. 文件**只存路径**，DB 不存文件内容

### 1.3 明确不做的事

- ❌ 不建客户表、合同表 —— 需求明确「客户名称」只是 Project 上的 varchar；红线 617 行「合同状态记个字段就行，别做合同全生命周期」
- ❌ 不建销售订单表 —— 业务模型追溯链里提到，但无对应实体，Project 承担
- ❌ 不建开票申请单/收款申请单 —— 隐含在Invoice / Receipt 内

### 3.2 主键策略 ✅ 已定稿：自增 ID

**业务模型 v6.0 原写**：「项目编号 = varchar 主键，非自增」。

**已拍板改为**：`id BIGINT AUTO_INCREMENT` 作物理主键，项目编号/单号降级为 `UNIQUE` 业务键。

**理由**：项目编号规则需求文档尚未定义（业务模型「未覆盖清单」第 6 条），一旦编码规则变更或跨期编号调整，用业务编码当主键意味着改主键 + 改七张子表外键 + 迁移历史数据 + 生产停机窗口，代价远高于收益。MyBatis-Plus 也默认期望自增/雪花 ID。

**业务侧无感**：对外 API 一律暴露业务编号，物理 ID 不出接口层。两者对外接口完全一致，差别只在数据库内部。

### 3.3 列名

小写蛇形。文档中 `ref` 类型的中文占位统一展开为 `xxx_id BIGINT`，`ref` 到字典编码的展开为 `xxx_code VARCHAR(64)`。

## 四、可扩展性设计 ★核心

需求方明确提出「后期可能会有字段补充」。本方案给出**三层预留**，各有适用场景，**不可互相替代**。

### 4.1 三层预留机制总览

| 层 | 手段 | 适用场景 | 优先级 |
|---|---|---|---|
| **L1 结构预留** | 全表统一审计字段 + 乐观锁 + 逻辑删除 | 几乎所有表都需要，**无条件预建** | P0 |
| **L2 弹性预留** | 每表 `ext JSON` 扩展列 | 后期加「少量、不影响查询和报表」的字段 | P0 |
| **L3 版本迁移** | Flyway `V2__` / `V3__` 增量脚本 | 加「核心字段」（进 WHERE、进报表、参与索引） | P0 |

**判断标准（加字段时选哪层）**：

```
新字段需要建索引 / 进 WHERE 条件 / 进报表聚合？
   ├─ 是 → L3：写 V{n}__xxx.sql，用 ALTER TABLE ADD COLUMN
   └─ 否 → 数量 < 5 且长期不改？
            ├─ 是 → L2：塞进 ext JSON
            └─ 否 → L3：老实 ALTER，别滥用 JSON
```

### 4.2 L1 · 结构预留（每张表都有）

```sql
-- 多租户（★已拍板预留，V1 全部默认 0，单租户跑通）
tenant_id     BIGINT       NOT NULL DEFAULT 0 COMMENT '租户 ID（企业），0 = 平台默认/未分配',

-- 审计字段（四件套，全表统一）
created_by    BIGINT       NULL COMMENT '创建人 ID',
created_at    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
updated_by    BIGINT       NULL COMMENT '更新人 ID',
updated_at    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP
                                ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',

-- 乐观锁（出纳并发审批必需，业务模型 2192 行明确要求）
version       INT          NOT NULL DEFAULT 0 COMMENT '乐观锁版本号',

-- 弹性扩展列（★预留核心）
extJSON       JSON         NULL COMMENT '扩展字段'
```

**`version` 为什么必须预建**：需求明确「出纳审批要加并发锁，防止重复审批」。MyBatis-Plus 乐观锁靠`@Version` + 该列，**表建好后再加会丢历史数据**，所以必须 V1 就带上。

**`ext` 的使用边界（必须遵守）**：
- ✅ 适合：后期加的展示型字段、临时开关、非检索型备注
- ❌ 禁止：金额、状态、任何需要 WHERE / 索引 / 报表聚合的字段
- ❌ 禁止：把已有核心字段挪进 `ext`（会导致查询困难 + MySQL JSON 无索引）

**`ext` 的 Java 映射**：
```java
@TableName(value = "fin_receivable", autoResultMap = true)  // ← autoResultMap 必须开
public class Receivable {
    @TableField(typeHandler = JacksonTypeHandler.class)
    private Map<String, Object> ext;
}
```

### 4.3 L1 · 多租户 `tenant_id` 预留 ★已拍板

技术栈文档定位为「云端多租户 SaaS」，`application.properties` L13 的多租户插件仍是 TODO。**V1 就要把列建好**，理由和 `version` 一样：**后补会丢历史数据**。

```sql
tenant_id  BIGINT  NOT NULL DEFAULT 0 COMMENT '租户 ID（企业），0 = 平台默认/未分配'
```

**加到哪几张表**：

| 表类别 | 是否加 `tenant_id` | 理由 |
|---|---|---|
| 业务主链 9 张（`fin_*`） | ✅ **加** | 租户隔离的核心，缺了就无法按企业隔离数据 |
| RBAC 7 张（`sys_role`/`sys_permission`/`sys_menu` 等） | ✅ **加** | 未来不同企业自定义角色/菜单 |
| `sys_user` | ✅ **加** | 同上 |
| `sys_org` | ✅ **加** | 组织架构天然是企业内的 |
| `sys_dict_type` / `sys_dict_data` | ⚠️ **加，但 V1 默认 0** | 字典分「平台级」与「租户级」，先用 0 表示平台字典 |
| `sys_config` | ⚠️ **加，但 V1 默认 0** | 同上 |
| `sys_audit_log` | ✅ **加** | 审计日志必须能按租户查 |
| `sys_process_def` | ✅ **加** | 流程定义将来可租户自定义 |
| `sys_file_storage` / `sys_file_download_log` | ✅ **加** | 文件属租户资产 |

> **结论：25 张表全部加 `tenant_id`，V1 全部默认 0（平台单租户模式）。**

**V1 的运行语义**：
```yaml
mybatis-plus:
  tenant-enable: false    # ← V1 关闭拦截器，单租户跑通
```
- V1 关闭租户拦截器，`tenant_id` 只作为**预留列**存在，不参与查询
- 上线前灌入的种子数据（字典、角色、菜单）统一 `tenant_id = 0`
- 将来开启多租户：改配置 `tenant-enable: true` + 灌真实 `tenant_id` 数据，**DDL 无需变更**

**开启后必须补齐的配套项**（V1 不做，但方案要留门）：
- `TenantLineInnerInterceptor`（MP 官方插件）
- 登录时注入 `tenant_id` 到上下文
- **所有唯一索引必须包含 `tenant_id`**，否则 A 企业和 B 企业不能有同名角色

⚠️ 最后一条是个坑：V1 时 `uk_role_code(role_code)`，将来多租户必须改成 `uk_tenant_role_code(tenant_id, role_code)`。**开启多租户时这批唯一索引要全部重建**，建议现在就把这一批索引起名统一为 `uk_tenant_*`，方便后续检索改造。

### 4.4 L1 · 逻辑删除三字段（按删除策略分层）

业务模型第 14 章的五层策略，直接决定哪些表带这三个字段：

| 层 | 实体 | 策略 | 带逻辑删除三字段 |
|---|---|---|---|
| 一| Receivable / Receipt / Invoice / WriteOff / ReturnOrder | **不可删，只能红冲** | ✅ |
| 二 | Project / Shipment / ShipmentLine / Item | 逻辑删除 | ✅ |
| 三 | Role / Permission / Menu / Org / User / ProcessDef | **停用代替删除** | ❌（靠 `status` 停用，不提供删除接口，无需逻辑删除） |
| 四 | FileDownloadLog / 草稿 / 临时文件 | 可物理删除 | ❌ |
| 五 | AuditLog | **只增不删不改** | ❌ |

```sql
is_deleted  TINYINT(1)   NOT NULL DEFAULT 0 COMMENT '逻辑删除：0否 1是',
deleted_at  DATETIME     NULL COMMENT '删除时间',
deleted_by  BIGINT       NULL COMMENT '删除人 ID'
```

MyBatis-Plus 侧统一配置：
```yaml
mybatis-plus:
  global-config:
    db-config:
      logic-delete-field: isDeleted
      logic-delete-value: 1
      logic-not-delete-value: 0
```

### 4.5 L3 · 迁移脚本策略

```
src/main/resources/db/migration/
├── V1__baseline.sql          # 25 张表 + 字典类型 + 基础字典数据
├── V2__init_dict_data.sql    # 业务字典初始值（状态机枚举等）
└── V3__...                   # 后续按需递增，只做 ALTER
```

**纪律**：
1. **V1 一经提交永不修改**（已部署过的库会校验 checksum，改了就报校验失败）
2. 后续变更只能新增 `V{n}__`
3. 脚本命名统一「动词_对象」，如 `V4__add_invoice_tax_rate.sql`
4. 每个脚本必须**可重复执行不报错**（用 `ADD COLUMN IF NOT EXISTS` 等幂等写法，或先判断 `information_schema`）
5. Flyway `baselineOnMigrate` 保持 **false**，避免对已有库误执行 V1

## 七、索引策略

### 7.1 通用规则

| 场景 | 做法 |
|---|---|
| 物理主键 | `id` 集群索引 |
| 业务编号 | **唯一索引**（`uk_*`），兼作查询索引 |
| 外键字段 | **普通索引**（`idx_*`），不建 FK 约束 |
| 逻辑删除 | 查询索引一律以 `is_deleted` **打头**，如 `idx_project_status(project_id, is_deleted, status)` |
| 组合索引 |遵循最左前缀，单表索引数 ≤ 6 |

### 7.2 为什么**不建外键约束**

需求文档未要求，且业务系统普遍不建 FK，理由：
1. `INVOICE → RECEIVABLE` 等强依赖**由应用层保证**（强依赖 = 业务规则，不是 DB 约束）
2. 避免批量导入、事务写入时被 FK 检查拖慢
3. 后期数据迁移/归档时FK 会成为阻塞
4. 逻辑删除场景下 FK 会造成"删不掉"（父行已软删，子行FK 仍指向）

> ⚠️ 这条要写进团队纪律，否则新人会问"为什么没建 FK"。

### 7.3 逻辑删除对索引的影响（重要）

MyBatis-Plus 逻辑删除会在 SQL 后自动追加 `AND is_deleted = 0`。若索引不含 `is_deleted`，会导致该字段索引失效。

**约定**：所有业务查询索引第一个排序列必须能在 WHERE 条件里体现，常用形态：
```sql
KEY idx_xxx_status (project_id, is_deleted, status)
```

## 八、事务与并发约束

### 8.1 核销单事务（业务模型 2314 行强制）

必须**一个事务内**完成三件事：
```
1. UPDATE t_receipt     SET written_off_amount = written_off_amount + ?
2. UPDATE t_receivable  SET written_off_amount = written_off_amount + ?
3. INSERT INTO t_write_off(...)
```
任一失败**全部回滚**。绝不允许「收款单核了但应收单没核」。

**建议**：`@Transactional(rollbackFor = Exception.class)` + 收付款两行加 `FOR UPDATE` 或直接用 `version` 乐观锁。

### 8.2 出纳审批并发锁

`receipt.approval_status` 更新处必须用 `version` 乐观锁，防止重复审批：

```java
// 更新失败即抛异常，业务层返回"单据已被他人处理"
int rows = receiptMapper.updateById(receipt);  // MP 自动在 WHERE 带 version
if (rows == 0) throw new BizException("单据已被他人处理，请刷新重试");
```

### 8.3 红冲链完整性

`Receivable` / `Receipt` / `Invoice` 三表字段对称：
```
doc_direction（蓝字/红字）+ original_xxx_id（指向原单）+ return_id（来源退货）
```
> ⚠️ 需求文档缺陷：Receipt 有`original_receipt_id`、WriteOff 有 `original_write_off_id` + `status`，但 **Receivable 的原蓝字单是否回标状态未说明**。本方案约定：**红冲不改原单状态**（红字单独立存在，靠 `original_xxx_id` 追溯），与业务模型 14.2 节「+10万 → -10万 → +8万」示例一致。**需产品确认**。

### 阶段 6 已落地：ORM 层分层口径

实体基类分三层，**不是过度设计，而是被 DDL 逼出来的**：

| 基类 | 字段 | 覆盖 |
|---|---|---|
| `BaseEntity` | id / tenantId / version / ext | 25 张全有 |
| `AuditedEntity` | 追加 createdBy / createdAt / updatedBy / updatedAt | 21 张 |
| `LogicDeleteEntity` | 追加 isDeleted / deletedAt / deletedBy | **仅 9 张 fin_ 表** |

**为什么审计四件套要下沉一层**：4 张 RBAC 关联表（`sys_user_role` / `sys_role_permission` /
`sys_role_menu` / `sys_role_conflict`）在 DDL 里**没有 `updated_by` / `updated_at`**——
关联关系只有「授权」没有「修改」语义。硬塞进基类会产生永远为 null 的僵尸字段，
并在每次查询结果里误导人。

**Mapper 纪律**：一律零手写 SQL 继承 `BaseMapper`；需要非 CRUD 查询时另建 XML
（拦截器的 SQL 改写对 `@Select` 注解拼的 SQL 不生效，逻辑删除会失效）。

**枚举纪律**：实体状态字段一律 `String`，**不写 Java enum**。枚举值归 `sys_dict_data` 维护，
新增一个枚举值不应该要求改代码 + 重新发版。前端展示时按字典翻译。

**三处对齐铁律**（改字段时必须同步）：DDL 脚本 / 实体类 / 本文档。
`EntityMappingConsistencyTest` 会自动校验 DDL 列与实体属性 100% 对齐，不一致直接构建失败。

## 附录 C：阶段 6 踩坑备忘（实现层，与上文设计互补）

1. **乐观锁必须 insert 填充，否则静默失效**
   insert 后实体 `version` 是 `null`（DB 侧 `DEFAULT 0` 但不回填实体），
   `OptimisticLockerInnerInterceptor` 会判定「调用方未启用乐观锁」直接放行，
   生成的 SQL 里**既没有 `SET version` 也没有 `WHERE version`**，`rows` 仍是 1。
   → `@TableField(value = "version", fill = FieldFill.INSERT)` + `MetaObjectHandler` 填 0。
   这是资金安全级别的坑：核销 / 审批并发写一旦丢了它就是数据错乱，且只断言影响行数发现不了。

2. **Javadoc 里禁止写 glob 路径**
   `classpath*:/mapper/**/*.xml` 中的 `**/` 会**提前闭合块注释**，
   后续中文全被当代码解析，报「非法字符」。第一反应容易误判成 GBK 编码问题。

3. **逻辑删除 + 唯一索引 ⇒ 测试不可重复跑**
   软删行仍在表里，`uk_tenant_project_no` 会撞 `DuplicateKey`。
   测试数据前缀必须带随机段，不能指望「上次已删」。

4. **本机 Maven 有两个，必须用 3.9.9**
   `C:\Program Files\apache-maven`（3.5.4，跑不了 `maven-compiler-plugin` 3.13，
   报 "requires Maven version 3.6.3"）；
   正确路径 `C:\Users\yhnce\.workbuddy\binaries\apache-maven-3.9.9\bin\mvn.cmd`。
   另：bash 里的 `mvn` 报 `ClassNotFoundException: Launcher` 是 shim 环境问题，
   **Maven 本身没坏**，走 PowerShell 调 `mvn.cmd` 即正常。

5. **MP 3.5.7 元数据 API 有限**
   `TableFieldInfo` 只有 `getTypeHandler()`，无 `hasTypeHandler()` /
   `isTypeHandlerEffective()`；`TableInfo` 无 `isWithResultMap()`。
   → 想验证 TypeHandler / `autoResultMap` 是否真生效，只能**真实读库**验证。

6. 单号生成规则仅定义了批次号 → 暂缓，其余字段已预留
