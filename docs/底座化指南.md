# 火星财务 · 底座化（可复用）指南

> 目标：把「平台内核」沉淀为可被别的项目依赖复用的底座 `firestar-core`，
> 把「火星专属业务」隔离在 `firestar-biz`，应用入口留在 `firestar-service`。
> 新项目复用底座时**只引 `firestar-core`，不引 `firestar-biz`**（火星业务不复用）。

---

## 一、模块划分与职责

| 模块 | packaging | 职责 | 依赖 |
|---|---|---|---|
| `firestar-core` | jar | 平台内核：RBAC / 字典 / 租户 / 菜单权限 / AI 中心 / 工作流 / 审计 / 文件 / 通知 等通用能力 | 仅第三方（Spring/Flowable/MyBatis-Plus…），**不依赖 biz/service** |
| `firestar-biz` | jar | 火星业务：项目 / 发货 / 退货 / 应收 / 发票 / 收款 / 核销 / 客户 / 商品 / 合同 等经营域 | `firestar-core` |
| `firestar-service` | jar（可执行） | 应用入口：聚合 core + biz，`@SpringBootApplication` 主类所在 | `firestar-core` + `firestar-biz` |

**依赖方向铁律**：`core` 绝不可反向 import `biz` 的类。否则分类脚本的级联规则会把它也拉进 biz。
判定脚本见 `scripts/`（见下），CI 可用它守住这条线。

---

## 二、复用方式

1. **私服 / 源码依赖**：把 `firestar-core` install 到私服，新项目在 `pom.xml` 里加
   ```xml
   <dependency>
     <groupId>com.firestar</groupId>
     <artifactId>firestar-core</artifactId>
     <version>${firestar-core.version}</version>
   </dependency>
   ```
2. **不引 `firestar-biz`**：火星业务是本项目专属，新项目若需要同类能力，应把对应代码**拷进自己的 biz** 或扩展 core，而非直接依赖。
3. `firestar-service` 的主类 `FirestarApplication` 扫描 `com.firestar`（默认 `scanBasePackages` 即包根），
   引入 core 后 core 里的 `@Component` / `@Configuration` 会被自动扫到，无需额外配置。

## 三、Flyway 迁移脚本规则（多模块）

迁移按「归属」拆到两个目录，**版本号保留原 V1–V108 不变**（不要在老版本里插号）：

| 归属 | 目录 | 内容 |
|---|---|---|
| 平台 | `firestar-core/src/main/resources/db/migration/core/` | 用户/角色/字典/菜单/权限/审计/通知/文件/工作流/Flowable 等 `V1–V108` 中平台相关的 66 个 |
| 业务 | `firestar-biz/src/main/resources/db/migration/biz/` | 项目/发货/退货/应收/发票/收款/核销/客户/商品/合同等 43 个（42 个存量 + V200 起新增） |

`spring.flyway.locations` 已在各 profile 配置为：
```properties
spring.flyway.locations=classpath:db/migration/core,classpath:db/migration/biz
```

> **新增业务迁移用 `V200+` 起号**，避免与平台 V1–V108 撞号；平台侧若需补充平台迁移，继续在 core 目录用 `V109+`。

校验：`SELECT COUNT(*) FROM flyway_schema_history;` 存量库应与 `66 + 42 = 108` 一致；此后每应用一个 `V200+` 新迁移再 +1（截至 V200 为 109）。
迁移内容改动后需同步 `DatabaseCheckService.readSeedData` 期望值（见《开发规范》第六节）。

## 四、种子完整性门禁

- `com.firestar.seed.SeedIntegrityValidator`（`@Component` `ApplicationRunner`）：应用启动后读全量 `sys_menu`，
  跑 `SeedIntegrityCheck`，发现 `route_path` 漏写 `/`、或 `MENU` 带 `perm_code` 却缺 `BUTTON` 子节点时**只打 WARN，不阻断启动**。
- `com.firestar.seed.SeedIntegrityTest`：纯逻辑单测，覆盖上述两种翻车模式（含 V108 式缺 `/`、V102/V106/V107 式缺 BUTTON），CI 里把它变成「测试失败」门禁。
- 新写菜单 / 权限迁移前，先通读《开发规范》第十一~十三节（RBAC 双线模型、BUTTON 节点、route_path 前导 `/`）。

## 五、基线重置脚本

开发期改动了 V1–V108 迁移内容、或想让某库从零重新全量应用迁移时，用 `scripts/reset_flyway.sql` 清空 Flyway 历史
（本项目的 `baseline-on-migrate=false`，残留历史会让 Flyway 拒绝与历史不一致的迁移）：

```bash
mysql -u<user> -p<pass> <db> < scripts/reset_flyway.sql
```

> ⚠️ 该脚本仅用于 dev/test，**生产严禁**。prod 应走正规迁移演进，绝不手工清历史。
> 新项目若从底座 fork 且不想继承 108 条火星迁移，可在引入 core 后对该库执行一次 `flyway baseline`
> （baseline-version 设为 `V108`），让历史从底座结束处接续。

## 六、前端 `src/views/system` 复用范围

前端平台管理视图位于 `src/views/system/`（`User` / `Role` / `Dict` / `Menu` / `Permission` / `Audit` / `Notification` 等），
属**平台层，可随底座一起复用**。业务视图（立项 / 发货 / 审批 / 应收 等）应放在独立目录，不复用。

复用时规则：
- 只搬 `src/views/system` + 对应的 `api/system/*`、`store/*` 中与平台相关的部分；
- 业务侧前端保持独立，依赖底座提供的接口契约（与后端 RBAC 双线模型对齐：`v-has-perm` 认 `BUTTON` 菜单节点）。
- 菜单 `route_path` 务必以 `/` 开头（见《开发规范》第十三节），否则从 `/system/*` 页签会相对解析成 403。

- [ ] `SeedIntegrityTest` 在 CI 跑过且通过？
