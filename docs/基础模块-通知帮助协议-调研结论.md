**关键判断 1：** SSE 骨架是「为互踢造的」，不是为通知造的。它的语义是「瞬时广播」——**连接断了事件就丢了**，没有补发、没有已读、没有历史。直接拿它当通知系统用，用户刷新页面就会丢待办提醒。**通知的可靠性必须由数据库事实表承担，SSE 只做「立刻响一声」的加速层。**

**关键判断 2：** 网关是**纯内存单实例**。当前 V1 单机部署没问题；一旦上多实例（V2 容器化），跨实例推送必丢——`SseRealtimeGateway` 头部注释已预留 `RedisRealtimeGateway` 的切换方案，接口不用改。**这条要在通知模块设计时就写进契约，不要让业务代码依赖「单实例」假设。**

**关键判断 3：** `sys_config` 已经存在，说明「系统参数」这条路是通的——但**没有页面**。如果新增一个「站点设置」页去存帮助中心开关、协议版本号，就会形成「sys_config 与站点设置双写」的第二套配置源。**必须二选一，不要并存。**

## 二、行业参照（成熟系统怎么做）

| 产品 | 通知 | 帮助 | 协议 |
|---|---|---|---|
| **SAP Concur** | Shell bar 铃铛 → 下拉列表 → 点通知直跳处理页；通知类型绑定「审批通过/退回/待付/连接异常」 | Shell bar `?` 图标 → In-app Help + 培训资源 + 社区；首页 Quick Actions / Company Notes 承接公告 | 登录前同意，账号级 |
| **飞书 / 钉钉** | 分组（私聊/群/@我/未读/免打扰）、未读红点、一键已读、文档内「当前文档通知」独立面板 | 帮助中心独立站 + 应用内嵌 | 隐私政策更新弹窗重新同意 |
| **金蝶 / 用友** | 工作台右上角消息中心，按业务单据类型分 Tab；待办与消息分离 | 帮助文档 + 新手引导任务 | 服务协议、隐私政策、SLA |
| **Notification Center 设计通则**（墨刀等） | ①未读 ≠ 未处理，红点只表达「看过没」②已读时机要固定（进详情加载成功才算已读）③批量「标记已读」不能顺手改业务状态 ④对象被删/权限收回时，详情要解释而不是留一个失效按钮 | 上下文帮助能把工单量降 20–35%；清单式 onboarding 控制在 3–7 项 | 同意要可撤回、可追溯、变更要重新取得 |

**提炼成三条设计红线（本项目的）**
1. **未读 ≠ 未处理。** 财务系统的「待审批」是业务状态，不能因为用户点开通知就变成已处理。通知只承载「你被叫了一声」，处理动作一律跳业务页完成。
2. **通知必须可跳转且可降级。** 点通知 → 跳到单据详情；单据已撤回/已删除/无权限时，通知详情要说明「单据已不存在或您无权查看」，而不是 404 或空白页。
3. **协议同意是法律证据，不是 UI 装饰。** 必须留版本号、时间戳、IP、UA、来源渠道，且**只能增不能改**。

## 三、通知模块设计

### 3.1 分层：通道 / 中枢 / 事实表

```
业务代码（审批、回款、开票、预算、借款、下载…）
        │  只调 NotifyService.notify(...)，不认识 SSE
        ▼
NotifyService（中枢：模板渲染 + 收件人解析 + 去重合并 + 落库）
        ├──→ sys_notification（事实表，可靠送达的根）
        └──→ ApplicationEvent → SseRealtimeGateway（加速层，在线即弹）
                                    │
                                    ▼
                        前端 铃铛红点 / Toast / 浏览器桌面通知
```

**为什么要这一层：** 业务代码直接 `publishEvent` 会退回到「SSE 即通知」的老路——离线即丢、无法查历史、无法多端同步已读。`NotifyService` 是唯一入口后，将来加短信/企微/邮件只是多一个 `Channel` 实现，业务侧零改动。

### 3.2 数据模型（Flyway V25 起）

| 表 | 用途 | 关键字段 |
|---|---|---|
| `sys_notification` | 通知事实表（一人一条，便于独立已读） | `receiver_id`、`type`、`title`、`content`、`biz_type`、`biz_id`、`link_url`、`level`(INFO/WARN/URGENT)、`read_at`、`read_channel`、`dedup_key`(唯一键防重复)、`expire_at` |
| `sys_notification_template` | 模板（管理员可改文案） | `code`、`type`、`title_tpl`、`content_tpl`(含 `{{变量}}`)、`channels`(站内/短信)、`enabled`、`version` |
| `sys_notification_pref` | 用户偏好（按 type 开关） | `user_id`、`type`、`inapp_enabled`、`desktop_enabled`、`sms_enabled` |
| `sys_user_guide_progress` | 新手引导完成度（帮助中心联动） | `user_id`、`guide_code`、`step_code`、`done_at` |

**索引要点：** `(receiver_id, read_at, created_at)` 支撑「未读优先 + 时间倒序」；`(receiver_id, type, created_at)` 支撑分类 Tab；`dedup_key` 唯一索引（如 `APPROVAL_TODO:{processInstanceId}:{assignee}:{taskId}`）防止重试产生重复通知。

### 3.3 第一期通知类型（对应需求文档的硬诉求）

| type | 触发点 | 接收人 | 跳转 |
|---|---|---|---|
| `APPROVAL_TODO` | 流程节点创建 / 加签 / 驳回重提 | 当前审批人 | 审批详情 |
| `APPROVAL_RESULT` | 同意 / 拒绝 / 驳回 / 全部完成 | 发起人 | 单据详情 |
| `RECEIPT_AUDIT` | 回款申请提交 | 出纳 | 回款详情 |
| `INVOICE_DONE` | 开票员上传并批准 | 销售经理 | 发票详情 |
| `BUDGET_ALERT` | 预算使用达 90% / 超预算 | 财务负责人 + 部门负责人 | 预算执行 |
| `LOAN_OVERDUE` | 借款逾期扫描（定时） | 借款人 + 直属上级 | 借款台账 |
| `SYSTEM_NOTICE` | 管理员发布 / 协议更新 / 版本发布说明 | 全员或按角色 | 公告详情 |

> 需求文档 2.4/2.7/2.9 明确要求「站内消息 + 短信/钉钉推送」「逾期提醒」，以及 3.1 的「多渠道通知」。第一期**先把站内做扎实**，短信通道复用现有 `SmsService` 抽象（若尚未落地则留接口），不为了「多渠道」牺牲「不漏、不重、可追溯」。

### 3.4 交互（对齐行业惯例，但不照搬）

- **铃铛 + 数字角标**放 header 右侧（全屏按钮旁），下拉面板 + 「查看全部」进 `/notice/list` 页。
- **面板**：分类 Tab（全部 / 审批 / 财务 / 系统）→ 列表（未读左侧圆点 + 类型图标 + 相对时间）→ 底部「全部标为已读」。
- **已读时机（固定规则）**：点击某条 → 先调 `POST /notifications/{id}/read` 成功 → 再跳转。列表滚动**不产生已读**。
- **桌面通知**：页面失焦且用户开启偏好时，用 `Notification API` 弹一条；必须在偏好里可关，且**只在用户已授权过权限时调用**，不主动讨要权限（讨要会打断财务操作）。
- **多端一致**：SSE 推的是「有新通知」的最小载荷（`{unreadCount, latest}`），不在推送里塞全文——避免推送与库不一致；前端收到后拉一次未读数（或直接 +1 再以接口返回值校正）。
- **不做**：不做「红点同时表示未读和处理中」的双语义；不做「删除通知」（财务审计场景，通知也是痕迹，只做已读 + 过期归档）。

### 3.5 维护侧
系统管理 › **通知模板**（编辑文案、开关渠道）、**通知记录**（管理员查全量、按类型/时间/接收人检索、支持「重发」——但重发走 `dedup_key` 变更避免重复）。

## 四、帮助中心设计（预留 Agent）

### 4.1 承载形态对比（需决策）

| 方案 | 形态 | 优点 | 代价 |
|---|---|---|---|
| **A 轻量（推荐）** | 内容存 `sys_menu`，点菜单右侧抽屉滑出文章，不离开当前页 | **零新菜单表、零新前端基建**、路由零改动；帮助与菜单同生命周期 | 无独立 URL 可分享；强 SEO 无意义（内网系统） |
| **B 独立一级目录** | 新增「帮助中心」CATALOG + 文章列表页 + 详情页 | URL 可分享、可放内部知识库 | 多一套列表/详情页面 + 一套内容表，收益与成本不匹配 |
| **C 外链** | `menu_type=LINK` 指向外部文档站（语雀/飞书文档/Confluence） | 内容维护完全外置，零开发 | 与系统割裂，无法做上下文帮助与 Agent 联动 |

**推荐 A。** 核心理由：帮助中心的价值 90% 在**「在出错的那一刻出现在眼前」**（上下文帮助把工单量降 20–35%），而不是「有一个能导航的文档站」。独立文档站（B/C）恰恰把用户从卡住的地方带走了。

### 4.2 内容模型：借用 `sys_menu`，不新建表

`sys_menu` 加两列：`help_content`（LONGTEXT，Markdown 源码）、`help_desc`（一句话简介，进页首的「这个页面用来干什么」）。内容与菜单**一对一、同生共死**——菜单删了文章自动跟着走，不会留孤儿内容；菜单改名/改路径不用维护两处。

- **渲染用 Markdown 源码 + `marked` + `DOMPurify`（或 v-html 前强制 sanitize）**，不引入富文本编辑器。理由：① 富文本 HTML 入库是存储型 XSS 的经典入口，财务系统一旦被打穿是合规事故；② 不引入 wangEditor/tinymce 这类重依赖；③ Markdown 足够写「三步操作 + 截图」。
- 截图走已有 `sys_file_storage`（OSS），正文里只存 `fileId`，渲染时换成签名 URL——**不存外链**，避免链接失效与越权访问。

### 4.3 三个入口（三件套）

1. **侧栏菜单项右侧 `?`**：hover 显示 `help_desc`，点击打开抽屉显示全文。`HelpTip` 组件统一封装，`admin` 角色额外看到「编辑本文」按钮 → 直接跳菜单管理编辑正文。
2. **header `?` 图标**：全局帮助抽屉，顶部搜索框（`/help/search?q=`，只搜 `help_content` 标题+正文，MySQL `LIKE` 足够，量级不过千条不需要全文索引）。
3. **更新公告**：版本发布时由管理员发布 `SYSTEM_NOTICE`，同时有一篇「更新说明」文章——用户看到通知点进去就是这次改了什么。

### 4.4 Agent 预留（关键：预留的是**接口与数据结构**，不是模型）

不做「先接个大模型」这种倒推式预留。真正要预留的是三件事：

| 预留项 | 现在就做 | 将来接 Agent 时 |
|---|---|---|
| 内容可被检索 | `help_content` 结构化 Markdown + 稳定的 `menu_id` 锚点 | 按 `menu_id` 切片做向量索引（embedding），检索命中带出处 |
| 提问入口 | 帮助抽屉底部「没解决？描述一下」→ 落 `sys_help_feedback`（问题、当前页面 `route`、用户 id、时间） | 同一入口换成对话；历史反馈直接成为种子语料 |
| 回答可落地 | 答案里必须带「跳转到该页面 / 打开这篇文档」的动作 | Agent 返回结构化 `{answer, actions:[{type:'navigate',path}]}`，前端按契约渲染 |

> 一句话：**现在把「内容—页面—提问」三者建立可寻址的关联，Agent 接进来只是换个答案生成器。** 反过来，如果现在只做一个静态文档页，将来接 Agent 要重做内容结构。

### 4.5 新手引导（可选，建议放第二期）
登录首周在工作台展示 3–5 项清单（完善个人信息 → 查看项目 → 提交/审批一张单据 → 下载一次发票），完成度存 `sys_user_guide_progress`。业界的经验值是清单能显著降低首周求助量，但**清单必须绑定「激活事件」而不是「看过某页」**。

## 五、使用 / 隐私协议维护设计

### 5.1 为什么必须单独做（不能只放一段静态文字）

依据《个人信息保护法》第 14/15/17 条 + 《个人信息保护合规审计管理办法》（2025-05-01 施行）及其审计指引，需要满足：
- 处理目的、方式、种类**变更时必须重新取得同意**；
- 必须提供**便捷的撤回方式**；
- 必须**对同意操作进行记录**（"完整留存告知文本、同意记录、变更与重新同意、撤回同意等证据，做到可回溯、可证明、可审计"）；
- 规则变更要**及时告知**。

→ 这意味着：**协议是「带版本的内容对象 + 带证据的同意记录」，不是一个 HTML 文件。**

### 5.2 数据模型

| 表 | 用途 | 关键字段 |
|---|---|---|
| `sys_agreement` | 协议主体（一类型一条） | `code`(PRIVACY / TERMS / DPA)、`name`、`scope`(PLATFORM / TENANT)、`status` |
| `sys_agreement_version` | 版本（**只增不改**） | `agreement_id`、`version`(v1/v2)、`content`(Markdown 快照)、`change_summary`、`effective_at`、`need_reconsent`(bool)、`published_by`、`created_at` |
| `sys_agreement_consent` | 同意证据（**只增不删**） | `user_id`、`agreement_id`、`version_id`、`action`(AGREE / WITHDRAW)、`channel`(LOGIN / REGISTER / SETTINGS)、`ip`、`user_agent`、`created_at` |

**关键设计点：** 存 `version_id` 不存 `version` 字符串——文案快照必须能在三年后原样复现（审计要的是「他当时同意的到底是哪段文字」）。

### 5.3 交互

- **登录前/首次登录**：登录页底部「登录即表示同意《用户协议》《隐私政策》」（可点开阅读，不设勾选框——业界的「一揽子勾选」在合规上反而更脆弱）。**企业员工账号**建议改用「首登强制确认」弹层，记录 `channel=LOGIN`。
- **版本升级且 `need_reconsent=true`**：登录成功后由前端守卫拦截（在 `router.beforeEach` 的登录态分支内、拉 profile 之后）展示「协议更新」弹层：左侧更新要点摘要（`change_summary`）、右侧全文；两个按钮「同意并继续」/「不同意，退出登录」。**不做「不同意但继续用」**——那是无效同意；但也不能直接踢，要给「查看全文 / 联系管理员」的出口。
- **撤回同意**：个人中心 ›「隐私与协议」页，列出已同意协议 + 同意时间 + 版本，提供「撤回」按钮（二次确认 + 说明撤回后影响：如无法继续使用系统）。撤回写 `action=WITHDRAW` 的新记录，**不删旧记录**。
- **维护侧**：内容管理 › 法律协议 → 列表（类型 / 当前版本 / 生效时间 / 待重新同意人数）→ 新建版本（Markdown 编辑器 + 变更摘要 + 勾选「需重新同意」+ 生效时间）→ 可预览（模拟用户视角）。

### 5.4 合规清单（实现时逐条对照）

| 要求 | 落地位置 |
|---|---|
| 告知处理者名称与联系方式 | 协议正文固定章节（管理员可编辑） |
| 以清单形式列明收集的信息 + 目的 + 方式 | 隐私政策正文的「信息清单」表格章节 |
| 明确保存期限与到期处理方式 | 同上；与 `docs` 里下载记录 90 天等策略对齐 |
| 明确查阅/更正/删除/注销/撤回同意的途径 | 正文 + 个人中心实入口 |
| 变更及时告知 | 协议更新 → 同时发 `SYSTEM_NOTICE` |
| 同意记录可审计 | `sys_agreement_consent` 只增不删 + 管理端可导出 |
| 不因拒绝而拒绝提供服务（除必需） | 撤回后仅禁用系统（因属必需），文案需说明理由 |

## 六、菜单落位与权限点

| 位置 | 菜单 | 类型 | 权限点 |
|---|---|---|---|
| **header（无需菜单）** | 通知铃铛 / 帮助 `?` / 协议弹层 | — | 登录即可用 |
| 系统管理 | 通知模板 | MENU | `notify:template` |
| 系统管理 | 通知记录 | MENU | `notify:manage` |
| **内容管理**（新 CATALOG，sort 8） | 帮助文章 | MENU | `help:manage` |

### 10.2 SSE 路径治理（虎哥提出的问题，结论：思路成立，且比想象的更必要）

**问题复述：** `docs/nginx-sse-location.conf` 现在硬编码 `location /auth/stream`。将来每加一条 SSE 流（通知、审批推送、导出进度…）就得复制一份 location，`proxy_buffering off / gzip off / proxy_cache off / 两个 1h 超时 / XFF 透传 / X-Accel-Buffering` 全量重复一遍。

**这不是「不优雅」，是会出事的：** 这几项里任何一项漏配，nginx **不会报错**，只会让流静默退化——`proxy_buffering on` 时事件被攒成几秒一批或等到连接关闭才吐，前端表现为「实时推送时好时坏」，排查成本极高。**配置重复 = 漏配概率随模块数线性上升。**

**结论：采纳「单前缀，一次配置，多流扩展」。** 落到三层：

| 层 | 现状 | 改法 |
|---|---|---|
| 后端路由 | `/auth/stream`（挂在认证控制器下） | 拆出独立 `SseController`，统一前缀 **`/sse`**；首个端点 `GET /sse/realtime`（原 `/auth/stream` 保留 302 或直接下线，二选一，建议直接下线 + 前端同步改，避免两套并存的过渡期维护成本） |
| Spring Security | `/auth/stream` 靠 `anyRequest().authenticated()` 兜 | `/sse/**` 用 `permitAll()`，**认证放到端点内部**（复用 `AuthController.stream` 现有的 token 解析 + `current_jti` 比对逻辑，401 语义原样保留）。原因：SSE 请求可能不带 Authorization（EventSource 无法带头）或走 query token，放行后在端点里统一裁决，比在 filter 链上开特例更可控 |
| nginx | `location /auth/stream {...}` | **只写一条 `location /sse/ {...}`**，一次性配齐 SSE 三关 + 超时 + XFF + `X-Accel-Buffering: no`；之后新增任何流只要路径在 `/sse/` 下，零配置 |

**两个必须写进注释的坑（否则下次一定踩）：**

1. **绝不能用 `location ^~ /sse`**。`^~` 会短路该前缀下的所有内部跳转，而 SPA 的 `try_files ... /index.html` 依赖内部跳转兜底——写成 `^~` 后，`/sse/foo` 收到非 SSE 响应时不会回落 `index.html`，直接 404。**用普通前缀 `location /sse/`，靠 longest-prefix 在 `/` 之前自然命中即可。**
2. **`/sse/` 的匹配优先级高于 `location /`，但低于正则 location**。若站点配置里有 `location ~* \.(js|css|png)$` 这类正则，且 SSE 路径带了这类后缀（不会，但仍要写清楚），会被正则抢走。规则：**所有前缀 location 写完再写正则**，或用 `location ^~` 之外的方式保证顺序（nginx 的匹配规则是「先最长前缀，再按顺序试正则」，前缀 location 里不能有正则）。

**否决「一个 topic 一条连接」：** 有人会顺理成章地认为「既然按业务扩展路径，那通知走 `/sse/notify`、审批走 `/sse/approval`」。**不行。** 用户开 5 个 Tab × 3 个 topic = 15 条并发长连接，HTTP/1.1 浏览器同域上限 6 条，直接互相阻塞，页面其他请求全排队。**正确做法：一条连接 `/sse/realtime`，消息体内带 `topic` 字段，前端 `subscribe(topic, handler)` 分发。** nginx 侧仍然只有一条 location，扩展的是回调注册，不是连接数。

```java
// 消息体契约（网络层只有一条流）
event: NOTIFY            // 事件类型 = topic/kind
data: {"topic":"notify","payload":{...},"ts":1697990000000}
```

### 10.3 Token 过期与 SSE 长连接（补充一个第一轮没讲透的点）

**事实（已读代码验证）：**
- `JwtProperties.expiration = 7200000L`（**2 小时**）。
- `JwtAuthenticationFilter` 的写法是：`if (header != null && header.startsWith("Bearer "))` 才解析，**没有 token 时直接 `chain.doFilter` 放行**，最终落到 SecurityConfig 的 `anyRequest().authenticated()`。
  ⚠️ **这里原写「拦成 401」是错的，2026-10-18 在 ECS 实测证伪：实际返 403。** 根因与影响见第十一章 11.3。
- `SseRealtimeGateway.SSE_TIMEOUT_MS = 3_600_000L`（**1 小时**），比 token 的 2 小时短——这是当前一个被掩盖的事实：连接在 token 过期前就因 1h 上限被服务端关掉，前端重连才遇到 exp 校验。

**推论与对策：**
1. 一条 SSE 连接**可能活得比 token 久**（1h 连接 vs 2h token，若用户 1.5h 时建立连接，token 还剩 0.5h，连接能活到 2.5h）。**不要指望 token 过期自动断流来登出**——这是安全假象。
2. 真正的兜底是前端**已经存在的** `/auth/session-check` 5 秒心跳：token 过期 → 401 → `handleSessionExpired` 弹重新登录。SSE 只负责「在线即可推送」，不承担鉴权生命周期。
3. **服务端不要主动扫描 exp 去断流**：`SseEmitter` 的 send 是异步的，主动断流会与 `onCompletion` 回调竞争，且需要额外的调度线程。保持简单：流只管活着，鉴权归心跳。
4. **前端重连才会拿到 401**，所以断线重连路径必须保证 401 分支能优雅落到 `handleSessionExpired`（现有 `realtimeClient.ts:51-66` 已实现，保留）。

### 10.4 「强制刷新 / 版本发布通知」的 SSE 通道（补一个真实需求）

`SecurityConfig` / `JwtAuthenticationFilter` 之外还有个隐患：**前端发版后，旧 Tab 的 chunk hash 失效**，用户点导航会 `Failed to fetch dynamically imported module`。`realtimeClient.ts` 已有「拿到 200 但不是 `text/event-stream` 就按失败处理」的防御，但 5.6 时代的 SPA 长开 Tab 是常态。

**设计：** 复用一个 `refresh` 事件（不新增连接）。`SseRealtimeGateway` 现有 `broadcast` 就是遍历全部 user（`connections.keySet()`），若在广播里 `send(comment("refresh"))`，前端 `readStream` 当前会把注释行直接丢弃（`line.startsWith(':')` 不处理），所以需要把注释帧改成带语义的命名事件：

```java
// 网关现有 onRealtimeEvent 的 else 分支（username == null 时）
broadcast(RealtimeEventType.NOTIFY, payload);
// 但「刷新」不能走 NOTIFY（前端会当通知弹窗），新增枚举：
public enum RealtimeEventType { FORCE_LOGOUT, APPROVAL_CREATED, APPROVAL_DONE, NOTIFY, APP_RELOAD }
```

前端 `realtimeDispatch` 加 `case 'APP_RELOAD': location.reload()`。后端由运维/发布脚本调一个受权限保护的管理端点 `POST /api/sse/broadcast-reload` 触发（仅 ROLE_ADMIN）。**这是「发版后陈旧 Tab」问题的正解，比 `chunk-load-error-stale-deploy` 的「捕获后提示刷新」更主动。** 该项列为 P4 可选。

### 11.4 实测撕开的一个老 bug：未认证请求返 **403**，不是 401

> 这是本次改 nginx「顺手捞出来」的东西，与本轮改造无关但必须记：它会影响 P0 验收。

**现象：** 无 Authorization 头请求任何非白名单接口 → `403`（本轮 `/sse/realtime`、`/socket/test`、`/api/auth/stream` 三个都验到了）。

**根因（读代码确认，不是猜）：**

```java
// SecurityConfig.filterChain
.authorizeHttpRequests(auth -> auth
    .requestMatchers("/auth/login", "/ping", ...).permitAll()
    .anyRequest().authenticated())
// ↑ 没有配 exceptionHandling().authenticationEntryPoint(...)
```

`JwtAuthenticationFilter` 的写法是 `if (header != null && header.startsWith("Bearer "))` 才解析——**无 token 时直接 `chain.doFilter` 放行**。于是请求以 anonymous 身份走到 `anyRequest().authenticated()` 被拒；由于没有配置 `AuthenticationEntryPoint`，Spring Security 6 在没启用 formLogin/httpBasic 时的**默认入口点是 `Http403ForbiddenEntryPoint`** → 返 **403**。

**三条连带影响：**

1. **`AuthController.stream()` 里那三段 `throw ResponseStatusException(UNAUTHORIZED, ...)` 全是死代码。** 捋一遍就知道到不了：无 token → Security 层已 403；token 过期/无效 → `JwtAuthenticationFilter.writeUnauthorized` 抢先写 401 并 `return`；jti 不匹配（被顶号）→ 同样在 filter 第 73-77 行被拦。**controller 里的兜底一次都不会执行。** 它给人「这里有人兜着」的错觉，实际是装饰。
2. **与前端契约不符。** `realtimeClient.ts:51` 是 `if (res.status === 401)` 才走「会话失效 → 弹重新登录」。一旦因为任何原因请求漏带了 Authorization（storage 被清、登出瞬间正好赶上一次重连、未来切 EventSource 传不了 header），拿到 403 → 不弹重新登录，而是走**指数退避无限重连**。用户看到的是「页面卡住不动」，很难归因。
3. **语义混乱。** 401 应为「未认证/该去登录」，403 应为「已登录但无权限」。现在两者混成 403，将来 P4 做按钮级/接口级权限时会被误导。

**建议修法（一处，约 6 行）：** 在 `SecurityConfig.filterChain` 里补 `exceptionHandling`，让未认证统一返 **401**，且 JSON 格式与 `JwtAuthenticationFilter.writeUnauthorized` 保持完全一致（前端依赖 `code`/`message` 字段）：

```java
.exceptionHandling(e -> e.authenticationEntryPoint((req, res, ex) -> {
    res.setStatus(HttpServletResponse.SC_UNAUTHORIZED);
    res.setContentType("application/json;charset=UTF-8");
    res.getWriter().write("{\"code\":401,\"message\":\"登录已过期，请重新登录\",\"data\":null}");
}))
```

⚠️ 这会**改变全站所有接口的未认证响应码**，影响面较大，**需虎哥拍板后才动**。同时建议：改完后把 `AuthController.stream()` 里那三段不可达的 401 判定删掉或改成明确注释，避免留下误导性代码。

> **2026-10-18 更新：虎哥已拍板「现在就改，统一 401」。** 实际改动与本地实测结果见 **11.5**。上述三条连带影响中，第 1 条（不可达的死代码）与第 2 条（前端契约）已在同批处理。

### 11.8（补充记录：前缀收敛完整决策，与上方 11.8 重复，保留备查）

**决策**：虎哥拍板——SSE / WebSocket 不再作为裸前缀例外，统一纳入全站 `/api` 体系。
这是一次**设计原则的重大调整**（之前特意让 SSE 绕过 `/api`，现在纠正）。

**关键事实（决定了改法，不是不重要）**：firestar 后端**没有全局 `/api` 前缀**——
所有 controller 都是 `/system/...`、`/auth`、`/sse`、`/files` 这种裸路径；前端统一走 `/api`
是靠 vite 的 `rewrite` 把 `/api` 剥掉实现的。WebSocket (`/socket`) 后端至今无 handler（纯预留）。

**改法（对后端零入侵）**：代理层把 `/api` 剥掉。
- nginx：`location /api/sse/` + `proxy_pass http://127.0.0.1:2025/sse/`（带尾 URI 剥前缀）；
  `/api/socket/` 同理带 `/socket/`。后端 `SseController` 一行不用动。
- 前端：`realtimeClient.ts` 的 `ENDPOINT` 从 `/sse/realtime` → `/api/sse/realtime`；
  `vite.config.ts` 删掉独立的 `/sse` 规则，改 `'/api/sse'`（rewrite 剥 `/api` + 关缓冲），
  **必须写在 `/api` 通用规则之前**，否则会先命中通用规则丢失关缓冲。

**改动文件**：
- `docs/nginx-sse-location.conf`：整份重写（注释、两段 location、坑 2 同步改为"故意带尾 URI 剥 /api"）。
- `firestar-manager/vite.config.ts`、`firestar-manager/src/utils/realtimeClient.ts`：前缀 + /api 体系对齐。
- ECS `/etc/nginx/nginx.conf`：备份 `bak_20261019_100042`；两 location 块正则替换 + `nginx -t` 通过 + reload。
