### Step 0-A 日志收口（P0，先做）

**双因归因，缺一不可**：
- 内容量来源：`application-dev.properties:34` `logging.level.root=debug`（`com.firestar` 也是 debug）
- 无回收机制：`bin/start.sh:266` `nohup java -jar ... >> "$LOG_FILE" 2>&1`；且 **无 `logging.file.name` 配置、无 `logback-spring.xml`** —— 全靠 shell 重定向，永不切割

**改法**：
1. `application-dev.properties`：`logging.level.root` **debug → info**；`logging.level.com.firestar` 保留 `debug`（业务日志仍全量）；新增 `logging.level.org.flowable=warn`。
2. **不引入 `logback-spring.xml`**，改用 Spring Boot 原生配置（已在 `application.properties` 统一加）：`logging.file.name=logs/app.log` + `logging.logback.rollingpolicy.max-file-size=20MB` / `max-history=15` / `total-size-cap=300MB`。原生滚动策略开箱即用，避免手写 XML 出错、改动更小。
3. **`bin/start.sh` / `bin/deploy.sh` 的重定向必须同步改**为 `>> "$LOGS_DIR/console.log"`。
   - 不改 → **双写**（logback 写 app.log + shell 也写 app.log），日志反而更大。
   - **不能改成 `/dev/null`**：`bin/start.sh:292~300` 的健康检查逻辑是**从 app.log 里 grep `[startup-health]` 行**。`StartupHealthReporter` 是走 logger 写的，走 logback 后仍会进 app.log，所以改成 console.log 安全；但改完**必须实测这一步仍能取到结论**，否则部署门禁静默失效。
4. 历史 450MB：归档为 `logs/app.log.20261021.bak` 或直接删除，不留在原地。

**DoD**：重启后连续跑 10 分钟，`app.log` 增长 < 1MB/分钟；手工 `grep "\[startup-health\]" logs/app.log` 有命中；`bin/start.sh` 健康检查退出码 0。

**两条实施纪律**：
1. 关引擎后**必须实测启动**。Flowable 各 starter 之间有隐式依赖（典型：idm 关掉后某些 `IdmIdentityService` 注入失败）。一次全关后启动报 `NoSuchBeanDefinition` 就逐个回退二分定位，**不要**盲目把所有开关改回 true。
2. **V3 里的 62 张引擎表一张都不要删**。V3 已进库（Flyway checksum 锁定，脚本永不修改），关引擎后多出来的表闲置无害；删表反而破坏已提交迁移的可重放性。

补充：`FlywayBeforeFlowableConfig` **不需要改** —— 它按 bean 名包含 `engineconfiguration` 匹配，引擎少了几个照样给剩余引擎追加 `dependsOn`。

### Step 0-C IDM 决策（P1，**虎哥 2026-10-21 已拍板**）

**拍板结论：关 Flowable IDM（`flowable.idm.enabled=false` 见 0-B），身份主权全留自研 RBAC。**`assignee` 存 `sys_user.id`（稳定全局唯一，优于会变 username）；`ROLE` 节点用 `candidateGroups = sys_role.role_code`，`USER` 节点直接 `assignee`；**不双写 `ACT_ID_*`**（双写一致性噩梦）；`LEVEL` 逐级审批用 `sys_user.parent_id` / `sys_org.leader_id` 链在映射层计算，Flowable 不感知。具体取 parent_id 链还是 org.leader_id 链在 Step 2 配置节点生成时定。

理由（三条，任一条单独成立即够）：
1. 技术栈文档「关键集成点①」原文就是「Spring Security + Flowable **共享**用户体系」——共享的对象是我们的 `sys_user`，不是 Flowable 的 `ACT_ID_USER`。
2. 双写用户进 IDM = 两套用户表同步，离职/调岗/改角色必然不一致（同类问题的代价已在别处吃过）。
3. Flowable 的 `assignee` / `candidateGroups` 本质就是字符串，不校验用户是否存在。我们的 userId 和 roleCode 天然能填进去，零成本。

**前置改造**：Step 1-C 的 `CurrentUser`，所有审批代码通过它拿 userId。

### Step 0-D 驳回语义前置论证（P1，**虎哥已授权 POC；POC 不过不写业务代码**）

> **状态：已授权**。A2 拍板「走论证线路」——先写 3 节点 demo（无业务代码）验证 `skipBeforeSeq` + 排他网关方案，POC 项 1~5 全绿后才进 Step 2/3。

需求规则（业务模型 §4.4 原文）：**驳回到节点 X → X 及之后所有节点全部重走，X 之前的跳过**；同时 §4.3 要求「驳回节点之前的已审批记录保留」。

引擎能力与缺口：

| 能力 | Flowable 原生 | 缺口 |
|---|---|---|
| 把执行从当前节点挪到任意已定义节点 | 有：`runtimeService.createChangeActivityStateBuilder().processInstanceId(pid).moveActivityIdTo(cur, target).changeState()` | — |
| 「X 之前已审过的节点跳过，不重新生成任务」 | **无** | 引擎只认当前执行位置与已完成历史，不理解"业务上这个节点已经算通过了" |
| 审批意见保留 | 有：`ACT_HI_COMMENT` 全量留 | 需要区分"本轮有效 / 上轮已失效"，否则 UI 会把上轮意见当成有效结论展示 |

**推荐方案（方案 1，POC 已验证）**：流程变量 `skipNodeIds`（`Set<String>`，存放「已审批通过且非驳回目标」的节点 nodeId）+ 每个节点完成后挂**排他网关**：
```
网关判断 !skipNodeIds.contains(本节点nodeId) → 生成 UserTask（重走）
        skipNodeIds.contains(本节点nodeId)   → 走默认分支跳过（不生成任务，写一条 system comment）
```
> ⚠️ **POC 修正（2026-10-21）**：原 `skipBeforeSeq = 驳回目标节点的 seq` + 条件 `nodeSeq > skipBeforeSeq` 有**边界 bug** —— 驳回到 A(seq=1) 时 `nodeSeq(1) > 1` 为 false，连 A 自己都会被跳过，悖离「X 及之后重走」。改用 `skipNodeIds` 集合（记录已审过的非目标节点）才正确，已在 `PocRejectSkipTest` 验证通过（见 src/test）。
驳回时：`moveActivityIdTo(当前, 目标)` + `setVariable("skipNodeIds", 已审过且≠目标的节点集合)` + `setVariable("rejectTargetNode", 目标nodeId)`。

**否决方案（方案 2）**：重启一个新流程实例、把之前的审批结论作为预置变量注入从头跑。
否决理由：`ACT_HI_*` 会断裂成两条实例，审批历史页要合并两个 processInstanceId 才能展示，且 `fin_project.process_instance_id` 只能存一个 —— 数据模型被迫改，得不偿失。

**意见复用**：`ACT_HI_COMMENT` 不动，加业务侧 `round`（第几轮）概念：每次驳回-重提 `round+1`，写入 comment 的 `type` 或 `action` 字段。详情页按 `nodeSeq` + `round` 展示「本轮 / 历史轮」。

**POC 清单（Step 3 开工前必须全绿，3 节点流程即可验证）**：

| # | POC 项 | 通过判据 |
|---|---|---|
| 1 | 动态生成 3 节点 BPMN → 部署 | `ACT_RE_PROCDEF` 新增 1 行，`VERSION_=1` |
| 2 | 发起 → A 同意 → B 同意 → 停 C | `ACT_RU_TASK` 逐个流转；`ACT_HI_ACTINST` 齐全 |
| 3 | C 驳回至 A | 执行跳回 A 并生成新任务；B 的待办不存在 |
| 4 | A 重新同意 → **B 自动跳过** → 停在 C | **B 无新任务**（这条是需求最硬的一条，不过就别往下做） |
| 5 | 改节点配置重新部署 | `ACT_RE_PROCDEF` 出现 `VERSION_=2`，且 version=1 的在途实例**仍按旧流程走完** |

## 三、Step 2：配置节点（流程定义管理）

### 2.1 `node_list` JSON Schema（**必须先定死再写代码**）

`sys_process_def.node_list` 现在只是 `JSON` 列，无任何约定。建议结构（写进本文档即为契约）：

```json
[
  { "seq": 1, "nodeId": "node_1", "name": "部门主管审批", "type": "ROLE",  "assignee": "ROLE_MANAGER", "rejectable": true },
  { "seq": 2, "nodeId": "node_2", "name": "财务审批",     "type": "USER",  "assignee": "12",           "rejectable": true },
  { "seq": 3, "nodeId": "node_3", "name": "总经理审批",   "type": "LEVEL", "assignee": null,           "rejectable": false }
]
```

| 字段 | 约束 |
|---|---|
| `seq` | 从 1 连续递增，服务端校验不跳号 |
| `nodeId` | `node_{seq}`；**一旦部署不可改**（它是 Flowable 的 activityId，改了等于换节点） |
| `name` | 可随时改，重新部署生效 |
| `type` | `USER` 指定人 / `ROLE` 角色（运行时解析成人）/ `LEVEL` 逐级（按 `sys_org` 往上找） |
| `assignee` | `USER` 填 userId；`ROLE` 填 roleCode；`LEVEL` 留空 |
| `rejectable` | 该节点是否允许驳回（业务模型 §4.1「可否驳回」） |

### 2.2 动态 BPMN 生成

用 Flowable 的 **`BpmnModel` API**（`org.flowable.bpmn.model.*` + `BpmnXMLConverter`），**禁止手拼 XML 字符串**：

- 手拼第一个坑是 `&` / `<` 转义，第二个坑是命名空间前缀，第三个坑是中文字符集，第四个坑是改一个节点要动整个字符串模板 —— 这四条都是必踩，不是概率问题
- `BpmnModel` 有类型约束，拼错在编译期或部署期就报，不用等到运行

生成骨架：
```
startEvent → [网关: seq > skipBeforeSeq] → userTask(node_1) → ... → userTask(node_N) → endEvent
                ↓ 否
           自动通过（不生成任务，写 system comment）
```

### 2.3 版本管理

| 动作 | 行为 |

### 3.3 流程编排

```
POST /projects/{id}/submit
  ├─ 校验：approval_status ∈ {PENDING_APPROVAL, REJECTED}
  ├─ 校验：当前用户是 sales_manager_id 或 created_by
  ├─ 首次提交：WorkflowEngineService.start("project_approval", businessKey=projectId, vars)
  │              → 回写 process_instance_id + approval_status=APPROVING
  └─ 驳回后重提：moveTo(当前, rejectTargetNode) + 变量 round+1（见 3.4-4）

POST /approvals/{taskId}/approve  { comment }
  ├─ 校验任务归属（assignee 命中 或 candidateGroup ∈ 当前用户角色）
  ├─ complete(taskId, vars, comment)   // 意见写 ACT_HI_COMMENT
  ├─ 流程结束 → fin_project.approval_status = APPROVED
  └─ 通知下一节点审批人（APPROVAL_TODO）

POST /approvals/{taskId}/reject   { targetNodeId, reason }
  ├─ reason 必填（业务模型 §4.3「必须填写驳回原因」）
  ├─ 校验 targetNodeId ∈ 已审批节点 ∪ {发起人}
  ├─ 写 comment + setVariable(skipBeforeSeq, targetNodeId 的 seq) + round+1
  ├─ moveTo(当前 activityId → targetNodeId)
  └─ 通知发起人（APPROVAL_RESULT）
```

### 3.4 关键实现细节（**每一条都是会踩的坑**）

1. **审批人解析 `AssigneeResolver`**
   - `USER` → `assignee = userId`
   - `ROLE` → `candidateGroups = roleCode`
   - `LEVEL` → 按 `sys_org.parent_id` 往上找同 roleCode 的人；**找不到必须抛业务错**，不能静默让流程卡在无人可审的状态（这是最难排查的故障）

2. **待办查询必须两个条件**：`taskAssignee(userId)` **和** `taskCandidateGroupIn(roleCodes)` 都要查。
   只查 assignee → 角色节点的任务永远不出现在任何人待办里（最常见的实现遗漏，且测试时如果先用「指定人」节点测，根本发现不了）。

3. **驳回跳转 API 名**：`runtimeService.createChangeActivityStateBuilder()` + `.moveActivityIdTo(...)` + `.changeState()`。
   ⚠️ **接口文档 §10 末尾写的 `createChangeActivityStateBuilderInstance()` 这个方法名不存在**（已核对 Flowable 7.1.0 的 `RuntimeService` 接口）——照文档抄会编译不过。

4. **重新提交**：驳回后任务落回发起人（若 `targetNodeId` 指向发起人）或直接落回被驳回节点。发起人改完内容调 `moveTo` → 需要变量 `rejectTargetNode` 记住目标节点。

5. **乐观锁**：`fin_project.version` 已预建（V1 就有，建表方案 §8.2 明确为「出纳并发审批」准备的）。审批状态回写必须走 `@Version`，否则并发双击会重复流转。

6. **金额红线**：`fin_project.contract_amount` **禁止前端传入**，提交时只做校验不写入（建表方案 §红线，业务模型 2191 行）。

7. **通知接入**（P2 已有中枢，直接调，不要另建通道）：
   ```java
   notifyCommand.code       = "APPROVAL_TODO" | "APPROVAL_RESULT";
   notifyCommand.bizType    = "PROJECT";
   notifyCommand.bizId      = projectId;
   notifyCommand.linkUrl    = "/approval?bizId=" + projectId;
   notifyCommand.dedupKey   = "APPROVAL_TODO:" + taskId + ":" + receiverId;  // 同节点重启不重复提醒
   ```

8. **审计接入**（`@Auditable` 机制已写明「未来财务/审批模块直接复用」）：
   ```java
   @Auditable(operationType = "APPROVE", targetType = "PROJECT",
              targetIdSpEl = "#result", entityClass = Project.class,
              fields = {"approvalStatus", "processInstanceId"})
   ```

ExclusiveGateway gw = new ExclusiveGateway(); gw.setId("gw_skip"); process.addFlowElement(gw);
process.addFlowElement(seqFlow("f_start_gw", "start", "gw_skip"));
// 每个节点后挂网关：!skipNodeIds.contains(nodeId) 才生成任务，默认流跳过（示意，完整见 POC 测试）
process.addFlowElement(seqFlowConditional("f_gw_task", "gw_skip", "node_1",
        "${!skipNodeIds.contains('node_1')}"));
process.addFlowElement(seqFlowConditional("f_gw_skip", "gw_skip", "end",
        "${skipNodeIds.contains('node_1')}"));

// 用户任务
for (NodeCfg n : nodeList) {
    UserTask t = new UserTask();
    t.setId(n.nodeId);
    t.setName(n.name);
    if ("USER".equals(n.type)) t.setAssignee(n.assignee);
    if ("ROLE".equals(n.type)) t.setCandidateGroups(List.of(n.assignee));
    if ("LEVEL".equals(n.type)) t.setAssignee("${levelResolver.resolve(execution)}");
    process.addFlowElement(t);
}
